service in Kuala Lumpur and the Klang Valley. It presents service discovery,

## 11. What Codex did poorly and corrections

Every lesson follows EVENT -> WHY -> DETECTION -> CORRECTION -> RESULT -> RULE.

1. **Misleading static hero cue.** The first implementation showed 01 / 04
   without carousel behavior. Phase 2.5A detected VIS-01; Phase 2.5B removed it.
   Rule: every affordance needs behavior or a clearly static label.
2. **Mobile destination focus gap.** Navigation did not reliably focus the target.
   A11Y-01 detected it; controlled focus behavior corrected it. Rule: test focus,
   not only scroll or URL.
3. **Supporting type below the floor.** TYPE-01 found reduced readability;
   supporting type was adjusted. Rule: define and review a typography floor.
4. **Tablet overflow missed earlier.** Phase 4A reproduced 113 px overflow at
   768 px and corrected the layout. Rule: include intermediate tablet widths.
5. **Automated tests arrived late.** Phase 3.5 still had a testing gap. Phase 4A
   added 8/8 API tests. Rule: create a minimum test harness with the first API.
6. **API hardening arrived late.** Body size, encoding, caching, and timing were
   tightened in Phase 4A. Rule: define boundary policy at API design time.
7. **Hydration uncertainty remained unresolved.** A diagnostic never reproduced.
   No speculative change was made; status stayed NOT REPRODUCED / ROOT CAUSE
   UNKNOWN. Rule: do not fix a non-reproduced issue without a failing case.
8. **Performance optimization was not measured.** IMP-001 stayed P3/DEFERRED
   without production CWV evidence. Rule: measure before invasive optimization.
9. **Capability status needed explicit states.** Different tools were available,
   inspected, or partially executed. Dedicated ledgers corrected the ambiguity.
   Rule: record state transitions, not one boolean.
10. **Deployment capability was not assumed.** Owner used authenticated Vercel
    dashboard evidence because local CLI was unverified. Rule: detect deployment
    capability before promising automation.
11. **Warnings were documented.** Unsupported ESLint and install-script policy
    warnings were classified P2/P3 rather than silently normalized. Rule: record
    warning type, severity, and release impact.

## 25. Nexus reusable gates

These are PROPOSALS derived from Apex, not already-implemented Nexus features.

### Truthfulness gate

- Entry: a reference, copy deck, or demo claim exists.
- Checks: source, real/fictional status, disclosure, schema/indexing, contact and
  coverage proof.
- Evidence: content inventory, source, rendered route, metadata.
- Pass: every claim is sourced or explicitly fictional.
- Fail: unsupported proof is presented as fact.
- Unknown: source ownership or runtime state is unavailable.
- Owner boundary: real claims and guarantees need owner evidence/authorization.

### Capability execution gate

- Entry: a tool/skill is selected.
- Checks: installed, available, callable, executed, output, limitation.
- Evidence: command/tool output and environment state.
- Pass: execution level and output are recorded.
- Fail: output is attributed to an unexecuted tool.
- Unknown: availability or compatibility is unestablished.
- Owner boundary: paid/install/remote capabilities need authorization.

### Responsive matrix gate

- Entry: route is release-ready.
- Checks: 375/768/1024/1440, overflow, off-screen controls, menu, form, detail.
- Evidence: viewport measurements and screenshots/logs.
- Pass: required matrix has no known defect.
- Fail: overflow or inaccessible control is reproduced.
- Unknown: required viewport/tool unavailable.
- Owner boundary: device/browser expansion.

### Form/API boundary gate

- Entry: endpoint accepts user input.
- Checks: media, size, encoding, JSON, origin, honeypot, timing, headers, echo,
  provider side effects.
- Evidence: deterministic tests and live synthetic probes.
- Pass: required cases classify safely.
- Fail: unexpected side effect, echo, or unbounded input.
- Unknown: provider/storage cannot be inspected.
- Owner boundary: real delivery, retention, incident response.

### Accessibility evidence gate

- Entry: accessibility claim is requested.
- Checks: keyboard/focus/menu/labels/errors/status/alt/target size and tool type.
- Evidence: manual traces plus scanner/screen-reader output where available.
- Pass: claim is limited to methods run.
- Fail: claim exceeds evidence or defect remains.
- Unknown: scanner/screen-reader/WCAG capability unavailable.

- Entry: optimization or performance readiness is proposed.

- Evidence: dated production measurements.
- Pass: recommendation ties to measured impact.
- Fail: measured regression/budget breach.
- Unknown: only static/build/detector evidence exists.

- Checks: callable path, target project, env access, source SHA, rollback owner.
- Evidence: deployment record or authenticated dashboard.
- Pass: Ready deployment maps to accepted source SHA.
- Fail: mismatch or unauthorized target.

- Entry: public origin is selected.
- Checks: HTTPS, canonical/OG origin, env, robots, indexing decision.
- Evidence: live headers/metadata and settings.
- Pass: origin references agree.
- Fail: mixed origin, preview leak, false indexing.

- Checks: application/docs SHAs, Git status, deferred list, untracked evidence,

- Evidence: Git and release records.
- Pass: reproducible state and owner decision recorded.
- Fail: drift or undocumented blocker.
- Unknown: remote SHA or evidence unavailable.
- Owner boundary: reopening or next phase.

## 26. Capability-state model lesson

Apex demonstrates that these states differ:

INSTALLED -> package/files exist.
AVAILABLE -> environment says capability may be used.
CALLABLE -> this session can invoke it.
EXECUTED -> an invocation happened.
INSPECTED -> source, guidance, or output was reviewed.
APPLIED -> advice affected a decision or implementation.
CONCEPT ADOPTED -> a concept influenced a native design.
IMPLEMENTED -> application code contains the behavior.
VALIDATED -> a specified check produced evidence.

Examples:

- Bencho was inspected and its press-feedback concept was adopted, but no
  Bencho block was implemented.
- Impeccable was callable for a source detector but only partially usable because
  the URL detector lacked a compatible browser.
- UI UX Pro Max was conceptually relevant but unavailable for the review stage.
- A build passing proves the build command completed; it does not prove
  Lighthouse, CWV, WCAG, or live delivery behavior.

Nexus should store these as separate fields or state transitions, never one
boolean used value.
