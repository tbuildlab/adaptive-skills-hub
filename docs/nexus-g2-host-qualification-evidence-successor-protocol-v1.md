# Nexus G2 Host Qualification Evidence Successor Protocol v1 — PROPOSED

Status: **PROPOSED FOR OWNER REVIEW; NOT ACCEPTED; NO EXECUTION AUTHORITY**

Scope: the fixed, empty-capability, secret-free local LPAC qualification configuration, HQ1–HQ5 only.

Controlling baseline: accepted *Host Qualification Scope & Exit Decision v1* and its acceptance record at `c5129fd0e1ed0d1ec5b2fe97c95d0d43f3405724`.

## 1. Authority and finite boundary

This document proposes replacement **evidence mechanisms**, not replacement security properties. The present `LPAC-Local-Delivery-v1/package/05-local-qualification-protocol-v3.md` and accepted Owner Release amendment/specification remain controlling until a separately reviewed, owner-accepted successor and any necessary bounded architecture amendment expressly supersede named clauses. In particular, the pre-resume zero-entry PSS rule and current system-module mapped-byte rule still STOP the staged verifier. This proposal cannot authorize implementation, package V2, profile/process creation, Scenarios 01–04, E2B, HQ6 or G2. No prior owner release transfers.

HQ1 fixes actual execution provenance; HQ2 tests effective isolation; HQ3 excludes unauthorized execution inputs; HQ4 establishes containment, cancellation and recovery; HQ5 establishes trustworthy evidence. A missing, stale, nonindependent or contradictory required observation is **UNKNOWN/STOP** or **FAIL**, as specified below, never PASS. Local HQ1–HQ5 PASS, if later earned, is only for the exact local configuration; a network-capable LPAC and complete Host binding require separate qualification. A0–A6, Option D, Option A HOLD, the accepted package custody boundary, no-outer-Job requirement and four scenarios are unchanged.

The observation chain terminates at the independently reviewed owner-controlled package and exact finite verifier/controller/watchdog, Windows kernel, loader, token, process, Job, ACL and configured Code Integrity primitives, and owner-only postrun adjudication. It does not recurse into a verifier of the verifier or independently prove arbitrary Windows internals. Owner or SYSTEM compromise remains outside this local threat model. Every claim is bound to one attempt/package digest, fixed case, trusted-held process handle, PID plus creation time, event order, source and scope. A child report can corroborate but cannot establish PASS.

## 2. Exact successor rules

### 2.1 HQ3 — inherited and other security-relevant handles

**Threat/property.** An owner credential, file, process or other authority-bearing handle enters the LPAC child, or a later explicit/OS-opened handle reaches protected resources. The fixed local configuration has **no standard streams and zero permitted inherited handles**. Do not introduce a handle-list/stream variant in this successor.

**Before release.** The trusted controller records and independently verifies the exact `CreateProcessW` call for the fixed child: `bInheritHandles=FALSE`, no `STARTF_USESTDHANDLES` or inherited standard streams, no `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`, exact LPAC security capabilities, fresh allowlisted environment, `CREATE_SUSPENDED`, fixed application and working directory. It holds the returned process/thread objects, binds PID plus creation time, and queries `GetProcessHandleCount` on that **same still-suspended process** immediately after creation and again immediately before release. A zero count supports absence of pre-release handles only in combination with the creation policy and closed injection window; a nonzero count requires a bounded independent pre-release inventory classifying every handle by object identity/type, access and origin. An unclassified nonzero count STOPs; a count alone never proves provenance. Independently read back the child process security descriptor/effective access and establish that no unrelated/untrusted principal can acquire `PROCESS_DUP_HANDLE` or process-injection rights during the check-to-release interval; trusted owner/SYSTEM custody of the returned handle and all creation attributes must be explicit. If these rights or the interval cannot be bounded, STOP. A later process opening its own handles is a separate observation, not an inherited-handle PASS.

**First safe post-release barrier and operation.** Before child application code may reach the first security-sensitive operation, a trusted controller/OS-side observation must prove the barrier timing and inventory every then-open security-relevant child handle with object identity/type, granted access and a finite reason it is permitted. Repeat after the relevant operation. A working PSS snapshot is one candidate, not a mandated API; if PSS lacks the necessary detail, another documented bounded OS-side inventory must provide it. OS loader/runtime handles may be present only if identified and shown incapable of conveying owner secret or unauthorized effect authority. The creation-policy record, pre-release zero count **or complete nonzero inventory**, and closed external-duplication window establish **noninheritance**; later inventories establish **effective capability state**. Neither a count nor child self-report establishes both. Actual LPAC timing and deliberate inheritance, unauthorized duplication and extra-handle negatives must demonstrate detection without letting child application code act before the required barrier. Do not add open-ended kernel instrumentation to rescue a failed observer.

**PASS:** every creation/rights/pre-release count-or-complete-inventory fact binds the same suspended process; a demonstrated safe barrier yields complete relevant handle classification; post-operation observation and negatives agree, with no unauthorized handle. **FAIL:** observed inherited or unauthorized authority-bearing handle, bypass of the stated barrier, or a negative case not detected. **UNKNOWN/STOP:** unavailable count and inventory; nonzero count without complete pre-release classification; unbounded external duplication; unclassified/inaccessible later handle; missing safe barrier; inability to distinguish later state; or ambiguous event/process identity. If no bounded supported composition works on the actual LPAC configuration, this blocker requires a **new architecture decision**; there is no weaker local PASS. Residual risk is malicious owner/SYSTEM/kernel and Windows's own documented process/handle enforcement, explicitly in the TCB.

### 2.2 HQ1/HQ5 — actual loaded code and dependency closure

**Nexus-controlled code.** For verifier-launched controllers and recovery, controller-launched watchdog and LPAC probe/canary, and every actually loaded Nexus-controlled executable dependency able to affect the boundary, retain the accepted strong same-process rule: a protected, reviewed physical file object and hash/byte basis are held stable across check/create/load; a trusted OS-side creation/load observation binds that file object's volume/file identity and exact approved byte basis to the returned process (handle, PID and creation time) and the actual `MEM_IMAGE` mapping/base. For Nexus-controlled mappings, compare executable section bytes to the reviewed PE basis with only explicitly reviewed relocation/import normalization. Prove that the main-image gate precedes application instruction and that any later executable dependency is bound before its code can affect qualification. A null or unresolvable load-event file handle, uncertain ordering, unexplained mapping difference, unexpected writable dependency, path substitution or failure to hold the file/ancestor stable is UNKNOWN/STOP (a demonstrated substitution is FAIL). A hash before launch plus a path afterward is never sufficient. The child's assertion is corroboration only.

**Windows TCB/system code.** Nexus proves the actual same-process module load with a valid load-event file handle and mapping base, stable physical volume/file identity, protected canonical Windows component location, exact OS build and approved file/version/hash inventory, and positive Microsoft/Windows signature or catalog trust where the selected OS trust path requires it. It records the configured CI policy and relevant enforcement result, without demanding a per-module CI event that the platform does not promise. It rejects a writable, substituted, unexpected or unresolved physical system image. These signals must bind the **same actually loaded image**; a path, signature, CI event or file hash alone cannot PASS. If the event file handle is null, this proposal supplies **no automatic fallback**: STOP until a separately reviewed, supported OS-backed observation establishes the same mapped object's physical file identity and trust basis. The accepted Windows kernel/loader/CI TCB supplies the mapping of that verified system image into the process; Nexus does **not** require raw mapped bytes to equal raw file bytes and does not normalize undocumented `fothk` changes by guesswork. The observed `ntdll`/`kernel32`/`KernelBase` differences remain historically unexplained, not experimentally vindicated. If actual physical identity, trust basis or event ordering is unresolvable, STOP. This is a proposed bounded change to the accepted Owner Release mapped-byte promise, so a **separate explicit architecture amendment and protocol acceptance** are prerequisites to using it.

**Dependency closure.** The reviewed candidate inventory and OS/PDB anchors constrain expected load paths but never prove actual load. Establish the finite actually loaded code graph for each fixed component through same-process load events, including late loads before affected operations. Classify each edge as Nexus-controlled (strong rule above) or Windows TCB (bounded rule above); an unclassified executable edge is STOP. Revalidate after OS build, package, binary, dependency, CI policy or relevant loader-state drift. No speculative expansion of the 247-file/694-name static candidate inventory is required after the actual graph is closed. Windows internals behind an accepted system image remain in the Windows TCB, not a Nexus dependency recursion.

### 2.3 HQ1/HQ4/HQ5 — fixed watchdog

The same protected-package and actual-loaded-code rule applies to the exact watchdog and its relevant dependencies. A prelaunch file hash and ordinary `CreateProcessW` result are insufficient. One bounded candidate is a controller-owned, temporary debug observation of a **suspended watchdog** using same-process creation/load events, followed by explicit detach **from the watchdog only**, verified watchdog survival and a flushed owner-only ready receipt **before any qualification child is created**. This does not permit the separate owner-release verifier to detach from the controller or disable its kill-on-exit behavior. The temporary observation must not change the watchdog's required independent survival after controller loss; if debug lifecycle or pre-instruction ordering cannot be proven, STOP. The exact observation technique is conditional, not an implementation approval.

Controller and watchdog independently bind owner SID, non-elevation, no outer Job, exact attempt/package/case, process handle/PID plus creation time, Job identity and timer/deadline agreement. Watchdog readiness is a trusted OS/process observation plus owner-only flushed cross-record fact, not a watchdog self-asserted PASS. The watchdog must remain capable of terminating and verifying the contained tree after controller crash or stall. Before child creation, the watchdog's independent cleanup path must be alive and demonstrably able to survive controller loss; if a controller crash at this point could remove the only cleanup path, STOP. Job limits do not impose wall-clock time: the trusted controller timer and independent watchdog deadline trigger termination. Actual forced failure cases must show intervention, wait, zero-live reconciliation and no escaped descendant. No privileged service, Task Scheduler, generic launcher or additional verifier is introduced.

### 2.4 HQ1/HQ5 — finite owner-release verifier

The accepted one-command, one-verifier, four-case boundary stays fixed. The verifier proves its own owner SID/interactive non-elevated/no-AppContainer/no-outer-Job origin, package and ancestor custody/ACL/reparse/file-ID/hash stability, exact reviewed manifest and OS anchors, exact controller/recovery launch flags/environment/workdir, and actual same-process controller/recovery image and relevant loaded dependency identity under §2.2. It retains the exact process/debug connection and fixed new owner-only receipts, monitors late loads and reconciles outcomes; it does not detach from the controller, set debugger kill-on-exit false, run arbitrary commands, select a different package, create LPAC itself, act as an Agent Host or attest Windows internals. Its own bootstrap rests openly on owner-reviewed protected bytes plus the Windows loader/CI TCB, not a self-reported hash or a verifier-of-verifier. The verifier cross-checks watchdog evidence but cannot manufacture an unobserved watchdog load or replace controller/Job/LPAC observations. A verifier crash must not leave an unobserved controller or child; prove this in the fixed failure sequence.

### 2.5 HQ1/HQ4 — Application Control, owner path and outer Job

The observed CI 3077/3033 refusal belongs to the **Codex Desktop command path and staged bytes only**. It proves neither success nor refusal for a future exact binary in an ordinary external owner shell. Before local qualification, independently verify that the final reviewed verifier/controller/watchdog/recovery/probe/canary bytes needed by the case can actually launch through the authorized owner path under the unchanged Windows policy. A physical owner launch may be necessary after safe preparation and a separate exact-byte execution authorization; until then its result is UNKNOWN/OWNER ACTION REQUIRED. A block on that path is STOP; no CI/Device Guard disabling, broad allow rule, signing system, binary substitution or elevated workaround follows automatically.

The actual verifier, controller and watchdog each obtain a trusted `IsProcessInJob` observation bound to their process identity before creating the next child. **PASS** only when all return not-in-job, the verifier/controller creation flags omit breakaway, and Job assignment/verification precede LPAC child execution. In-job is FAIL for this fixed configuration; an error or missing same-process observation is UNKNOWN/STOP. A Windows shell opened from the UI is not evidence. This protects HQ4 against nested-Job semantics; no `CREATE_BREAKAWAY_FROM_JOB` is allowed.

### 2.6 HQ3 — environment, TEMP/TMP and working directory

Keep the present exact six-name fresh Unicode child environment (`SystemRoot`, `WINDIR`, `PATH`, `TEMP`, `TMP`, `USERPROFILE`), no standard streams, fixed synthetic workdir, protected owner package/evidence and redirected LPAC TEMP/TMP. The trusted creator records launch inputs, while an independent trusted/OS-side readback of the **same process** records effective name/value allowlist, actual redirected TEMP/TMP and workdir, observation source/scope and timing before sensitive work and at the accepted later barrier. Raw secret-bearing values are not copied into evidence; record nonsecret expected values or status-only match/difference. Verify protected path/ACL/object identity and negative owner-resource access. An unexpected name/value/path or access is FAIL; unreadable effective state, child-only report or substitution gap is UNKNOWN/STOP. This is bounded HQ3 input proof, not general Windows state attestation.

### 2.7 HQ4/HQ5 — fixed failure cases and cleanup

Run only the four accepted cases **after separate owner authorization** and only sequentially: 01 isolation/negative controls; 02 cancellation; 03 controller crash plus exact recovery; 04 controller stall/deadline. Keep descendant/breakaway/alternate-child negatives. Each case binds all receipts and OS observations to exact case, package, process and Job identities; the controller/watcher report actual termination request, waits and Job active count, while an independent owner/OS-side postrun check verifies the original PID plus creation time exited, Job active count zero and no escaped descendant or live experiment process. A PID by itself or a child receipt does not prove cleanup. Delete only this attempt's newly created profile/synthetic objects when positively safe; preserve historical evidence. Any ambiguous crash, stale receipt, unverified exit, orphan or cleanup discrepancy STOPs all later cases. Scenario 01 PASS plus cleanup gates 02, and likewise through 04. No local kill is evidence of remote cancellation, settled cost or E2B state.
