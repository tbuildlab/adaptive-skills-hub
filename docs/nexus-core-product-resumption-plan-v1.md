## Shortest route to a usable core

Use the existing Core Alpha 2 CLI immediately for its three supported trusted
local profiles. For a more useful conversational product, close the existing
planner-to-Host completion gap rather than build another planner/runtime.
OpenAI/Codex/Host supplies understanding, coding, tool invocation and replanning;
Nexus supplies the selected Skill, applicable scope, verification requirements
and truthful completion evidence.

The first flow is sequential. Choose a Skill workflow; an Agent persona may help
the Host apply expertise, but the first usable path does not depend on spawning
agents, G5, cloud custody, a database or remote admission.

Preserve existing Core local-hook approval semantics. For the new Host workflow,
use the user's task/session authorization for ordinary requested reads, scoped
reversible edits and local verification. Ask only for concrete dangerous actions
such as irreversible deletion, privilege/access changes, payment or external
publication where approval is required. Unknown executable provenance or a
missing Host capability must produce a clear blocker, not silent authorization.
Do not add a new identity provider, approval server or production authority path.

## Next slice: one Host-backed safe completion path

Proposed slice: **Nexus Core — plan, selected Skill, execute, verify, return**.
Start with one non-secret local project inspection and source-backed report task,
using an existing appropriate Skill and current Host file tools. This exercises
the entire flow on real project files without cloud provisioning or deployment.
After this path passes, apply the same small bridge to requested local coding
changes with ordinary tests; do not build a universal tool router first.

Minimal work:

1. One intake/continuation entry that uses the existing plan and selected Skill
   loading, then hands off to currently available Host tools.
2. A small completion record distinguishing selected, loaded, started, failed,
   verified and completed; include actual output/artifact references and checks.
3. Host approval only at required dangerous-action boundaries; no routine second
   approval for already authorized safe work. Keep local-hook `--approve` intact.
4. Return the actual finished artifact and concise result, rather than stop at
   plan/selection. Missing tools, failed verification or ambiguous effects stay
   explicit; no blind redispatch.

Acceptance: a fresh real local task selects and loads a real Skill, performs
actual Host work, independently reads/checks the output, returns the result, and
does not require routine approval. Negative cases must show unavailable-tool
refusal, verification failure and dangerous-action pause. Existing planner/Core/
MCP compatibility checks should remain passing. No G3/N01 research replay is
needed for these product acceptance checks.

Reuse the existing modules and Host Skill instructions; add only the missing
handoff/completion glue justified by this one path. Do not alter the frozen
Presentations mapping to pretend it already supports unrelated tasks. A precise
file ownership/change list will follow at slice implementation time; this plan
does not pre-commit to a generic framework or new network execution surface.
