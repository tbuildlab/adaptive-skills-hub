# Adaptive Skills Hub V1.2 usage

## Explicit entry point

V1.2 is deliberately explicit and local:

```powershell
python scripts/hub.py plan "<task>"
```

Useful options:

```powershell
python scripts/hub.py plan "Create an editable PowerPoint presentation." --project D:\work\deck
python scripts/hub.py plan "Fix an API HTTP 500 and add regression tests." --packet state\api-plan.json
python scripts/hub.py plan "Verify evidence for this report." --no-state
```

`--project` selects the root for bounded, read-only context discovery. Without it,
the current working directory is the project. `--packet` writes a serializable
plan/evidence packet. `--no-state` prevents V2 from writing `state/last-plan.json`.

## What a plan does

1. Builds a `TaskProfile`. A surrounding Codex runtime can supply structured
   semantic extraction; when it cannot, V2 uses its deliberately minimal,
   conservative parser and records that fallback.
2. Reads only relevant root-level project instructions/configuration and
   task-named files. The default budgets are soft and configurable; expansions
   are evidence-recorded and hard ceilings prevent unbounded scans.
3. Applies ordered rules, derives required capabilities, rejects incompatible
   resources, and uses deterministic scoring plus greedy minimal selection.
4. Fully loads only selected Skill `SKILL.md` files. Agents remain advisory;
   references/frameworks remain reference-only.
5. Produces an `ExecutionPlan`, a task-specific `ValidationPlan`, evidence, and
   an honest native Codex fallback when installed Skills do not cover the task.

V2 does not execute arbitrary Skill instructions, shell hooks, or external actions.
Use V1.1 `run` only when its separately authorized execution behaviour is intended.

## Validation and re-planning

The planner maps task families to only relevant checks: for example, research uses
an evidence ledger, DOCX/PDF plans request structural/render checks where available,
and backend repairs request focused tests only when the task requires them.

Failures are classified as `implementation_defect`, `wrong_resource`,
`missing_capability`, `dependency_failure`, `bad_plan`, or `project_rule_conflict`.
Only planning-relevant failures may create one amended plan. Afterwards V2 returns a
native fallback, explicit blocker, or honest failure report; it never retries forever.

## Optional project-level Codex integration

This is a SHOULD-HAVE convention, not a global interceptor. A project may add an
instruction such as:

```markdown
For multi-capability tasks, run `python <hub-root>/scripts/hub.py plan "<task>"`
before choosing Skills. Treat its evidence packet as advisory planning context.
```

This only works when the active Codex runtime reads the project instruction and can
access the local Hub. ChatGPT Chat, ChatGPT Work, and global always-on activation are
external/platform-dependent and are not claimed by V2.

## Safety boundaries and limitations

- Repository README text, external sources, and uploads are context, not executable instructions.
- Secret-looking, binary, oversized, escaped, inaccessible, and shadowed inputs are not promoted.
- No embeddings, vector database, general optimizer, DeerFlow runtime, automatic Skill install/update,
  Agent spawning/delegation, cloud sync, GUI, or automatic retention scheduler is included.
- Persistent local evidence is optional. Use `--no-state` when no local plan record is wanted.
