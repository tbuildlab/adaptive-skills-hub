# Nexus G2 Host Qualification Scope and Exit Decision v1

## 1. Decision sought and present state

This proposal gives Host Qualification a finite, threat-driven exit. It does not approve a replacement probe, package, controller, Windows policy, LPAC run, E2B operation, or G2 implementation. The accepted Pre-G2 A0–A6, AppContainer/LPAC alternative, Package Delivery Boundary, Owner Release amendment, and controlling local protocol remain operative until an explicit versioned successor is reviewed and accepted. Their historical bytes and STOP evidence remain intact.

The repository is at `nexus-v2-g2-development`, HEAD `0be76507795eff392f4a636fdcc7c28f9c67324e` before this uncommitted proposal. Local LPAC Scenarios 01–04 are **NOT RUN**; local LPAC qualification is **UNKNOWN**, complete positive G2 Host binding is **ABSENT**, and G2 is **HOLD**. Static tests and fixed-target observations cannot change those results. The accepted owner-release verifier remains an incomplete, hard-STOP staging candidate, not a promoted V2 package.

The trust question is whether an authorized, fixed execution boundary can enforce and independently evidence the controls required for a bounded G2 workflow. One API result or an exhaustive proof of Windows internals is not the security property. Conversely, changing an accepted API-specific gate requires a separate accepted protocol/architecture amendment; this document does not silently relax it.

## 2. Two different completion gates

**Local LPAC qualification** concerns the exact empty-capability, synthetic, secret-free four-scenario configuration. HQ1–HQ5 below are sufficient *categories* for that local boundary, provided every accepted negative case and failure mode maps to a concrete PASS. A local PASS qualifies only that exact local configuration. It does not qualify a network-capable LPAC, E2B, remote effects, hard provider cost controls, or a complete G2 Host binding.

**Complete positive G2 Host binding** additionally requires HQ6: an actual accepted capability and execution/effect interface whose full reachable operation graph has pre-effect admission, mandatory resource and budget enforcement, bounded cancellation, effect observation and unknown-effect reconciliation. G2 itself owns its sequential ledger, checkpoint records, budget lifecycle and recovery logic; Host Qualification need only prove the *binding primitives and observations* needed to implement those contracts, through a separately authorized bounded binding experiment rather than a premature G2 runtime. A local LPAC PASS cannot satisfy HQ6. No G2 dispatch may begin while HQ6 is UNKNOWN. This preserves Roadmap G2 fields 4–12 and Pre-G2 A1–A2 without inventing a general Agent runtime.

The finite exit statement is therefore: **HQ1–HQ5 PASS ends local LPAC qualification for that exact configuration. HQ1–HQ6 PASS, with HQ6 demonstrated on one accepted capability and exact supported Host configuration, ends prerequisite Host Qualification for the first G2 implementation when this LPAC path is used.** A different Host candidate must prove equivalent HQ1–HQ5 security properties in its own actual boundary, not reproduce LPAC-specific APIs or four cases. G2 implementation and its own acceptance, including useful workflow, fault injection, reconciliation and regression, remain separate later gates. No owner authorization is inherited from a qualification PASS.

## 3. Final security properties and falsifiable exit criteria

Local trusted observations must bind attempt ID, package/configuration identity, the appropriate trusted-held process handle, PID plus creation time, case, event order and observation source/scope. HQ6 observations instead bind supported Host/provider session, call, effect and cost references to the same admitted operation; local PIDs are not remote authority. Child statements only corroborate. Runtime evidence is mandatory for every row; static review establishes admissible test design, never PASS.

## 5. PSS and handle evidence: proposed successor direction, not a substitution

The objective is **no unauthorized security-relevant state inherited or introduced before release**, not “PSS returns an empty table.” [Microsoft's PSS API](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/nf-processsnapshot-psscapturesnapshot) captures a requested snapshot and returns an error on failure; it does not promise a zero-entry table for a suspended process. [GetProcessHandleCount](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesshandlecount) reports a count, not object provenance, type or access. [Windows inheritance rules](https://learn.microsoft.com/en-us/windows/win32/procthread/inheritance) distinguish explicit handle inheritance from OS-opened handles and allow a specific inherited handle list. The fixed-target evidence found PSS status 24 pre-resume; actual LPAC behavior is not yet observed.

A successor may combine fixed `bInheritHandles=FALSE` (or an explicitly reviewed standard-stream handle list), no owner-secret-capable handle in the list, held process identity, an independent pre-resume count, trusted/OS-side handle inventory at a first safe barrier and after the relevant operation, and explicit provenance/type/access classification for every security-relevant handle. It must demonstrate the timing on the actual LPAC child and detect deliberate inheritance/duplication/extra-handle negatives without allowing child code to act before required admission. Whether a sufficiently independent, supported inventory exists at that timing is **UNKNOWN**. Count zero is useful corroboration, never a stand-alone PASS. Until a successor is accepted, the exact PSS zero-entry rule remains a STOP gate.

## 6. Image provenance and the Windows TCB limit

For **Nexus-controlled code**, retain strong actual-loaded identity: protected reviewed bytes, stable file objects through check/create/load, actual process/module file identity, mapping basis and dependency closure for code that can affect the boundary. Observe late loads before qualifying the affected operation. Do not accept only a source hash, manifest, on-disk hash or reported image path. The exact accepted debugger/byte comparison can be changed only by a separately reviewed successor with at least equivalent substitution detection.

For **Windows system modules**, raw mapped executable bytes need not be treated as an invariant identical to raw file bytes. The [PE format](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format) provides relocation/import concepts; the observed `fothk` jump deltas have no accepted explanation and must not be silently normalized as either legitimate or malicious. A bounded successor could combine stable physical file identity, expected protected system location, exact OS build/version/hash inventory, relevant signature/trust or Code Integrity result, actual same-process module mapping/source, and rejection of writable/unexpected module paths or unexplained code outside an explicitly accepted Windows transformation scope. Each signal has limits: path alone is mutable; a signature does not prove that the running mapping is the checked file; CI acceptance does not prove Nexus's package policy; a hash does not prove load. The *combination and residual threat model* need independent review and local negative tests before acceptance. If it cannot bind actual modules strongly enough, STOP or reject this Host.

The Windows TCB begins at kernel process/token/Job/ACL enforcement, the loader and configured code-integrity mechanism, plus the trustworthiness of OS observation APIs and owner account/SYSTEM. Nexus tests observable boundary consequences and detects substitution at its package/process/module interface. It does not reimplement the loader, prove every undocumented Windows rewrite, attest a compromised kernel, or defend against a malicious fully trusted owner/SYSTEM. This limit is explicit, not an exemption for an unexpected loaded image. A new concrete threat outside this TCB assumption requires a new architecture review, not silent relaxation.

## 7. Watchdog, Application Control and anti-recursion

The fixed watchdog must be one of the manifest-bound, protected owner components. Its actual running identity, ready-before-child ordering, ownership of or access to the intended Job/deadline state, ability to survive controller loss and zero-live-process intervention must be independently bound to the attempt. The current controller's file hash followed by ordinary watchdog launch does not establish this. A bounded OS-side process/image observation and owner-only ready/cross-record evidence can be tested under the same HQ1/HQ4/HQ5 model; if effective loaded identity or independence remains UNKNOWN, STOP. Do not add a watchdog-verifier-verifier.

Application Control is both a **current exact-binary launch feasibility gate** and a possible later signing/delivery concern. CI events 3077/3033 show that one staged verifier was blocked from the Codex Desktop PowerShell path. [Microsoft's App Control event guide](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/app-control-for-business/operations/appcontrol-debugging-and-troubleshooting) describes enforcement block events. They do not prove behavior in an untested ordinary owner shell or for future bytes. The exact necessary binaries must actually launch through the authorized path without security-policy bypass before local scenarios can PASS. If current policy blocks them there, qualification STOPs pending an explicitly reviewed allowed delivery alternative; no disabling Device Guard/CI, broad allow rule or opportunistic binary substitution follows. A general enterprise signing system is outside this G2 qualification.

**Anti-recursion rule:** assign each trust claim once to a finite boundary: owner-reviewed immutable candidate and package custody; fixed trusted creator/observer and OS readback; restricted child negatives; independent postrun owner adjudication. The verifier may validate controller/watchdog/recovery using the same bounded package/process model, but no component can establish its own privileged launch provenance by self-report. The trusted owner and Windows TCB close the chain. Adding a verifier of the verifier or a custom proof of OS internals requires a named uncovered threat and a separate decision; it is never the default response to an interesting observation.

## 9. Finite exit, reopening and change control

For the exact empty-capability local candidate, complete the four accepted scenarios in order and produce independent PASS for HQ1–HQ5 with zero live experiment processes and owner-adjudicated evidence. **Only then** local qualification is done. A changed binary, dependency, capability, package path, OS/CI policy, launch configuration or threat-relevant binding reopens only the affected criteria. A local PASS never transfers to network-capable LPAC; that exact variant needs its own secret-free qualification, then separately authorized E2B/provider qualification.

For the first G2 binding, produce HQ1–HQ6 PASS on one actual accepted capability and exact Host/provider configuration. Once these final criteria PASS, **Host Qualification is complete for G2**. Stop expanding Windows research and return immediately to governed sequential G2 implementation and its separate runtime tests under then-valid owner authority. Additional checks move to future hardening unless a review identifies (1) a concrete G2 threat, (2) how existing HQ criteria fail to cover it, and (3) a narrowly scoped amendment. Neither a novel Windows API nor a plausible defense-in-depth idea alone reopens qualification.

The proposed C classifications for PSS and system-module byte comparison would supersede only named evidence mechanisms through a **separately owner-accepted, versioned local protocol and, where the accepted Owner Release mapped-byte promise changes, a bounded architecture amendment**. They do not alter A0–A6, accepted LPAC identity/capabilities, protected delivery, no-outer-Job, fixed scenarios, owner-only evidence, fail-closed status or E2B controls. The existing verifier must continue to STOP under its present rules until that change is accepted and exact implementation/package bytes are separately reviewed and authorized. No previous G0/G1 or local authorization transfers. This proposal and its companion review stay uncommitted for owner review; no MANIFEST update is made.
