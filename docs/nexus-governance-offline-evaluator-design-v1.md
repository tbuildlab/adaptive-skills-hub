## 2. Input, fixed output and no-effects contract

Input: one immutable bytes value encoding a single GovernanceAssessment `1.0`. Fixture wrappers and expected answers are never accepted as assessments. Caller supplies bytes; the function never opens/fetches a reference, expands a path, reads the environment/credentials, imports an input module, executes text, mutates the input or dispatches work. The exact 19-case documentary collection is the initial corpus; no actual task/provider/effect runs.

Output: deterministic inert report containing input-byte SHA-256, handling, structural status, bounded diagnostic codes/locations, input-position projections of declared check/applicability/outcome states, unresolved required checks, known declared failures and unknown profile positions. Codes/locations are generated by the consumer, not exception/source text. No raw claim/reason/locator/value/secret text or user-controlled ID is echoed. Input hash binds these numerical positions to the inspected bytes, not truth. Hashing is appropriate only because these are non-secret qualification-free artifacts; no protected credential bytes may be supplied.

Every output has literal `authority: "none"` and `dispatch_requested: false`; there is no task PASS, record approved/validated flag, recommendation-ready, grant, next action, install/activation, HQ/P grade or G2 readiness. Structural CONSISTENT means internal data coherence at the named checks only, never governance satisfaction.

## 3. Small deterministic behavior

1. Apply prototype-only input/resource guards: bytes only, at most 1 MiB, at most 512 entries per record list, at most 512 characters per ID. These are implementation resource envelopes for this offline artifact, not governance/API/task policy thresholds. Exceeding them yields REJECT_RECORD with a bounded reason; no property is marked absent or passed. A future change requires review of the prototype envelope, not a new universal task limit.
2. Use standard JSON decoding with duplicate-member rejection, no nonfinite values/BOM/unsupported syntax, bounded failure messages and caught decoding/recursion exceptions. No custom JSON grammar implementation. Catch excessive nesting as invalid/resource input, never “safe”.
3. Check only the exact documented member sets, required fields, scalar/array/object shapes, closed vocabularies and nonempty required explanatory strings. Null remains permitted only where the design permits it. No permissive unknown-member/version coercion. Both REAL and ILLUSTRATIVE are unverified declarations.
4. Detect duplicate IDs per namespace; resolve reference IDs and correct governance/evidence kinds without following locators; require bound governance revision; resolve profile/dependency/capability/diagnostic references. Verify supplied SHA-256 syntax only when present, not universally. Empty or missing required subject/source/evidence binding never becomes affirmative proof.
5. Reject N/A paired with a non-N/A outcome or a PASS paired with unresolved applicability/DEFERRED/N/A; reject PASS without an evidence association; reject a PASS whose listed mandatory dependency is null/UNKNOWN/FAIL/N/A or has unresolved applicability; reject missing dependency/cycle. Logical dependency checks are consistency analysis, not scheduling.
6. Otherwise retain the exact declared outcome/applicability states. Compute unresolved REQUIRED checks plus unresolved targets of `requires`; keep known FAIL distinct. Source-mandatory checks omitted/misclassified by the record cannot be recovered from arbitrary source text by this prototype; no closure is issued. DEFERRED requiredness and disputed classification remain review questions, never automatically waived.
7. Choose handling with fixed precedence: detected invalid structure/explicit contradictions => REJECT_RECORD; coherent recorded required null/UNKNOWN => PRESERVE_UNKNOWN; otherwise => REQUIRE_REVIEW. Unresolved applicability, unknown facts, known FAIL, diagnostic disputes and unverified PASS claims cannot yield acceptance. Retain explanatory flags/positions without rewriting any input claim. REQUIRE_REVIEW is not permission or a manual waiver of a mandatory property.

Only these predeclared checks run; no user rule expressions, dynamic policy maps, regular-expression claim parsing, verdict inference from words such as “authorized/fixed”, or external evidence resolver. All readable text remains inert. The result must not count its projections as observed capability/effect state.

## 4. Semantic limits and corpus expectations

The nine negative conceptual cases retain their manual rejection oracle. N01/N03/N04/N06/N08/N09 have mechanical structural/association/dependency contradictions. N02/N05/N07 additionally require understanding positive exclusion, diagnosis or independent authority; the consumer cannot certify those meanings. REQUIRE_REVIEW/PRESERVE_UNKNOWN are acceptable *offline handling* only because they confer zero acceptance and retain the mandatory gaps. They do not overturn the manual rejection.

A/C/D/E must REQUIRE_REVIEW rather than silently accept their conditional PASS. B/F/G and U01 retain recorded required UNKNOWN. U02/U03 REQUIRE_REVIEW. Adding a receipt/path/hash or switching ILLUSTRATIVE to REAL must not create accepted evidence/authority. Callable-to-executed/applied, session-to-authority, checkpoint-to-settlement and remediation-to-validation inference remain prohibited.

Needed tests: entire supplied corpus, unsupported/unknown members, duplicate JSON members/IDs, unknown refs/kinds, direct/transitive/cyclic dependencies, missing/null reasons, nonfinite inputs, bounds/type/nesting, stale-looking/source-disputed text retained for review, capability orthogonality, no raw output echo, deterministic repeat, unchanged input and no locator access. Test outcomes concern the offline function only, not the fictional tasks or provider/Host qualification.

## 5. Adversarial design review and anti-bloat

Separate pass by the same assistant: attack bogus source labels, fabricated evidence hashes, all-PASS synthetic input, REAL self-declaration, missing required gate selection, semantic credential/false-positive claims, hidden executable locators/text, mutable input/cache, duplicate/cyclic references, code/resource input and accidental registry registration. Design response: fixed zero-authority reports, no truth/selection completeness oracle, no ref access or text evaluation, immutable input, closed shape/version, bounded rejection, only structural consistency/uncertainty projection, no `ash`/registry changes.

Keep one public pure function and private fixed shape/graph helpers. No class hierarchy, DSL, rule plugin, generic graph library, executable schema, finding/history store, context/session subsystem, external fetcher, reporting UI or runtime hook. Built-in collections/JSON/hash functions suffice. Every added check must protect a documented structural distinction or this prototype's resource/output boundary; it cannot add normative requirements to tasks.
