# Nexus LPAC Fixed Owner-Release Verifier: Proposed Implementation and Qualification Plan v1

Status: **DESIGN ONLY — NOT ACCEPTED — NO BINARY OR PROFILE AUTHORIZED**
Depends on separate owner acceptance of `owner-release-boundary-amendment-proposal-v1.md` and a subsequent instruction authorizing implementation.

## Fixed source-level shape

One x64 C++ verifier, one compile-time table of four exact controller paths/digests, the exact case-03 recovery path/digest and case-specific receipt names, one bounded controller case at a time. No command-line parameters except a literal `--run-reviewed-local-qualification` activation marker; no path, arbitrary command, provider, capability, environment, deadline or policy selection. Exit immediately on unknown input. The table must be generated from a separately reviewed versioned manifest rooted at exactly `C:\Users\De Yong\NexusQualification\LPAC-Local-Delivery-v2\package` and verified as exact source bytes before build. The verifier has no E2B, credential, network, LPAC creation or G2 code. It may launch only the fixed case-03 recovery image at the accepted recovery point, after the crash/cleanup facts required by the protocol; an ambiguous controller disposition stops rather than triggering recovery or retry. Its recovery launch must pass the same suspended main-image, dependency, token, Job and evidence gates as every controller; recovery cannot be trusted merely because its path/hash is in the table.

The verifier first verifies its own owner token via `OpenProcessToken`, `GetTokenInformation` (user, elevation, integrity and AppContainer), session/interactive origin, and `IsProcessInJob`. It rejects an outer Job. It checks target/ancestor owner, protected DACL, effective DELETE/DELETE_CHILD rights, reparse attributes, volume/file IDs and manifest hash with `CreateFileW`, `GetFileInformationByHandleEx`, `GetNamedSecurityInfoW`/`GetSecurityInfo`, `GetFileAttributesW`, `GetFinalPathNameByHandleW` and reviewed effective-access logic. It uses fixed-path handles denying write/delete sharing where compatible with loader semantics; if it cannot hold every mutable ancestor and file stable, STOP. NTFS hardlink count and alternate-stream inventory must be observed; hardlink or ADS ambiguity stops. Never assume opening a file handle by itself protects a parent rename.

For each case it creates an exact process with `CreateProcessW` and `CREATE_SUSPENDED | CREATE_UNICODE_ENVIRONMENT | DEBUG_ONLY_THIS_PROCESS`, fixed application/command, fixed working directory, fresh allowlisted controller environment and no inherited handles. It uses the returned `PROCESS_INFORMATION` process/thread handles, `GetProcessTimes` creation time, `OpenProcessToken`, `IsProcessInJob`, `VirtualQueryEx` and `ReadProcessMemory`. Candidate independent image observations are `CREATE_PROCESS_DEBUG_EVENT.hFile/lpBaseOfImage` and `LOAD_DLL_DEBUG_EVENT.hFile/lpBaseOfDll`; `WaitForDebugEvent` and `ContinueDebugEvent` remain on the creating thread. Debug events must be matched to that exact process handle, PID and creation time. The verifier validates file IDs and SHA-256 with `BCrypt*` or an equivalent pinned Windows CNG path, plus PE headers/section-to-memory comparison with only reviewed relocation/import normalization. The main mapping and any dependency already observable while suspended must be bound before resuming. Later DLL loads must be bound at their debug events before their code can execute or affect a qualification operation. If an event file handle is null, file mapping differs, dependency is unlisted or observation ordering is unsafe, terminate and STOP. Close debugger-provided file handles after evidence is captured. Do not attach to unrelated processes, modify target memory, set `DebugSetProcessKillOnExit(FALSE)`, detach, or claim debugger events observe LPAC descendants.

An important **implementation feasibility gate precedes even static package promotion**: verify through a separate bounded, secret-free nonqualification test that the proposed `CREATE_SUSPENDED` + debugger event sequence can bind the main mapping and initial loads *before the controller's first application instruction*, and that the controller's own LPAC debugging remains intact. Microsoft documents event handles but permits null values; the necessary ordering cannot be assumed. No local LPAC scenario or real qualification controller may be used for this feasibility test without a separate owner instruction. A failure demands a new design review, not a weaker receipt.

The verifier keeps a debug loop through the controller lifetime to validate late loads before continuation and compares the live loaded-module set with the manifest closure. It records source/scope for each observation. It must show that the event represents the actual module loaded into the same process and that the event pause precedes module code that could affect the boundary. System DLL, API-set and KnownDLL resolution are explicit entries with OS build/file/PDB anchors. An unexpected executable mapping or callback path is STOP. A user-mode debugger cannot prove against a compromised kernel or an already malicious owner token; those remain outside the local TCB claim.

The proposed controller environment names are exactly `SystemRoot`, `WINDIR`, `PATH`, `TEMP`, `TMP`, `USERPROFILE`; resolve and freeze their values before implementation approval. `SystemRoot`/`WINDIR` identify the same reviewed Windows directory, `PATH` only its reviewed `System32`, `TEMP`/`TMP` the new owner-only `C:\Users\De Yong\NexusQualification\LPAC-Local-Delivery-v2\controller-temp`, and `USERPROFILE` the owner profile for this trusted owner process. Independently observe that same controller process's effective environment and relevant inherited/open handles, with source and scope recorded; extra names, changed values or inherited handles are STOP. If the fixed controller needs another name, first version and review the allowlist.

Receipt writes use fixed owner-only `evidence` names, `CREATE_NEW`, write/flush and exact file IDs; records contain no secrets or raw environment. A record includes manifest and verifier digests, four-case index, OS version, timestamps/monotonic sequence, subject SID/elevation/Job state, held file IDs/hashes, process-handle association, PID+creation time, main and dependency event IDs/bases/file IDs/hashes, memory-comparison scope, release state, any STOP code, termination/wait/cleanup observation and corroborating controller/watchdog receipt IDs. A missing or conflicting field prevents PASS. An independent postrun reviewer reopens authoritative evidence and verifies ACLs, IDs, hashes, process disposition and ordered cross-record consistency.

## Fail-safe and rollback

Before each `CreateProcessW`, ensure no prior case/receipt/process exists. On failure before creation, close handles and write a fixed failure record without creating any LPAC profile. On failure after creation but before release, terminate the returned process handle, wait and verify exit; preserve exact status, do not continue. After release, verifier loss must be covered by debuggee kill-on-exit plus the controller/watchdog/Job recovery already accepted, and independently tested with forced verifier crash. If debuggee termination or watchdog cleanup cannot be verified, preserve evidence, block every later case and require owner investigation. Never remove the historical C: package or D: evidence. Abandon a failed new package version in place and prepare a separately reviewed version; do not silently rewrite.
