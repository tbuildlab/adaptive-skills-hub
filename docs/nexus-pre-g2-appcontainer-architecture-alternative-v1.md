# Nexus Pre-G2 AppContainer Execution-Boundary Alternative v1

Decision ID: `nexus.pre-g2.appcontainer-execution-alternative.v1`

Version: `1.0.0`

Date: 24 September 2026

Status: **PROPOSED ARCHITECTURE ALTERNATIVE — NOT ACCEPTED — NO IMPLEMENTATION OR RUNTIME AUTHORITY**

## 1. Decision sought and present state

This proposal considers a fixed-purpose, owner-created Windows Less Privileged AppContainer (LPAC) as the local restricted E2B data-plane client. It is **Alternative 3**, not a way to satisfy the accepted trusted-launch decision's conditional Option A. The accepted state remains **Option D**: there is no positively qualified G2 Host binding, no accepted source for an owner-controlled `NexusTest` primary token, and no independently verified trusted launch. The accepted separate-account E2B protocol remains authoritative unless a separately reviewed and owner-accepted successor replaces its affected provisions. No existing G0 authorization transfers to this new mode.

The `NexusTest` model is proposed for replacement **for this candidate only** because the owner controller cannot obtain that account's primary token without an unaccepted credential, privilege, or broker boundary. Earlier positive account, directory and status-only credential checks do not establish the required clean launch. An ordinary same-user subprocess with a cleaned environment is still insufficient: it retains the owner's effective resource access. The proposed alternative relies on Windows AppContainer's additional package identity, capability checks and low integrity, subject to actual negative tests on this machine. Microsoft documentation describes possible mechanisms; it is not evidence that this configuration works here.

Nothing here edits or weakens accepted Pre-G2 A0–A6, the frozen Roadmap V2/G1/R2/R4/R5 surfaces, the accepted trusted-launch HOLD, or the historical G0 attempts. Acceptance of an architecture successor would permit only separately authorized, bounded investigation. It would not authorize a launcher, AppContainer profile, E2B Sandbox, first untrusted command, G2 implementation or dispatch.

## 2. Exact proposed trust boundary and principals

| Principal or component | Proposed authority and custody | Explicit exclusion |
| --- | --- | --- |
| Trusted owner controller | A non-elevated De Yong process, operating under a reviewed exact binary and owner-controlled evidence location. It predeclares the attempt, creates and verifies the LPAC process, retains its process/thread/Job handles, and requests bounded cancellation. In a later, separately authorized E2B G0, only this principal may use the owner-protected E2B control credential for create/detail/cleanup. | No LocalSystem, `SeTcbPrivilege`, `SeDebugPrivilege`, password transfer, generic privileged broker, arbitrary executable/argument interface, or untrusted code in this process. |
| Restricted local data-plane client | One fixed, reviewed LPAC process created by the controller from the controller's own Windows logon. Its token retains the De Yong user SID but must also carry the **exact attempt-specific AppContainer package SID**, the approved capability set, the LPAC policy, and Low integrity. It receives no owner control credential or owner SDK object. | The user SID alone is not isolation evidence. The client cannot become an Agent runtime, shell, general HTTP proxy, arbitrary URL/command dispatcher, or source of its own launch attestation. |
| E2B guest subject | In a later G1-only stage, one separately authorized untrusted synthetic process within the bound microVM. | No owner API key, bearer/OIDC session, local owner profile, control-plane SDK object or local process handle. |

The proposed security boundary is the intersection of ordinary user/group access and AppContainer package/capability access, plus Low integrity, explicit creation-time controls and independently verified resource ACLs. LPAC is the **only** variant proposed for the first local experiment. A regular AppContainer, a restricted token without AppContainer, or a same-user sanitized process is not an automatic fallback. Windows may virtualize some AppContainer profile paths under the owner profile; that fact alone is neither a secret leak nor proof of isolation. Effective access to owner secrets must be negatively observed.

## 3. Identity and capability contract

Before a future local experiment, its owner-approved protocol must pin one new moniker, one attempt ID, the derived package SID and an exact no-reuse profile rule. `CreateAppContainerProfile`/the documented profile mechanism and `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` are candidate native facilities. The controller must hold the returned process handle and query **that same process's** token: `TokenUser`, `TokenType`, `TokenIsAppContainer`, `TokenAppContainerSid`, `TokenCapabilities`, integrity/elevation, groups/privileges and session/logon identity where available. The expected user SID is the owner's, **not** the `NexusTest` SID. The package SID and capability set, not a child-printed identity string, identify the restricted principal. Any absent, extra or mismatched field is a STOP or FAIL under Section 7.

For the first secret-free local experiment, the capability list is **empty**, with LPAC opt-out of the broad All Application Packages grant. No network capability is granted. A later proposed `internetClient` or other network-capable LPAC variant requires separate owner authorization and a complete secret-free isolation qualification of its **actual** executable/dependency bytes, package SID/LPAC token, exact capability set and launch configuration **before G0 provider creation, G1 review, token handoff or any real E2B use of that variant**. The empty-capability PASS cannot satisfy this gate. `internetClient` grants broad Internet reachability and is **not** an exact-host allowlist. No `internetClient` grant, endpoint change or network probe follows automatically from an empty-capability PASS. `internetClientServer`, `privateNetworkClientServer`, `broadFileSystemAccess`, `runFullTrust`, `enterpriseAuthentication`, `lpacCom`, `registryRead`, location/device capabilities, arbitrary custom capability SIDs, and any wildcard/all-applications grant are prohibited in the first local experiment. Any later requested capability requires a versioned security review and a new exact test; missing or contradictory evidence stops release, and inability to run with the accepted capability set is not permission to add one.

AppContainer's documented process and credential isolation does not certify denial for the owner credential target `Nexus-E2B-G0-Control`. The fixed local probe may call `CredReadW` under the independently verified LPAC process token and return only success/failure and the Windows status code; it must never read back, print, copy, hash, log, or persist a returned credential value. A successful lookup is FAIL and terminates the attempt. The owner controller must separately verify the probe binary, token and return-channel binding; a child status alone is corroboration, not launch proof. Denied attempts to open/list the owner repository, owner-only evidence, browser/session material, credential paths and owner processes must also be status-only. Do not broaden those resources' ACLs to make the test run.

## 4. Fixed image, directories, environment and handles

The future experiment must predeclare one absolute executable path, reviewed source/build identity, expected SHA-256 and a bounded load/dependency graph. Before creation, the controller resolves reparse points, records volume/file identity, verifies owner-controlled ACLs deny LPAC write/replace and validates the exact file bytes. Its qualification evidence must close the check-to-create replacement window by holding the verified file objects stable against write/rename/replace through creation, or by an equivalent independently verifiable OS-backed mechanism; path equality or a pre-launch hash alone is insufficient. It must use the explicit application path rather than shell or PATH resolution. While that same created process is suspended, trusted controller/OS-side evidence must bind its **loaded image file identity and byte basis** to the predeclared reviewed artifact, not merely read back its image path. The same stable-object, loaded-identity and reviewed-byte rule applies to every executable dependency that can affect the boundary, including modules loaded after resume: observe and bind those loads to the same process before treating the affected operation as qualified. If the actually loaded executable or relevant dependencies cannot be independently verified and bound, STOP. No arbitrary command line or unsigned/user-writable plugin is allowed.

The controller constructs a fresh Unicode environment block from an exact, reviewed list. For the local probe, the allowed names are **exactly** `SystemRoot`, `WINDIR`, `PATH`, `TEMP`, `TMP` and `USERPROFILE`: `SystemRoot`/`WINDIR` identify the same resolved Windows installation, `PATH` contains only that installation's reviewed `System32` directory, `TEMP`/`TMP` identify the attempt's AppContainer-private temporary directory, and `USERPROFILE` identifies only the attempt's synthetic private profile root. The exact resolved values must be frozen before any separately authorized experiment. Microsoft documents AppContainer redirection of `TEMP`/`TMP` into its profile; trusted controller and/or OS-side observation of the **same process's effective environment** must compare supplied values, OS-resolved targets and actual child-visible values, including the redirected TEMP/TMP paths. Record the independent observation source, scope and allowlisted effective names/nonsecret values; child self-report may corroborate but cannot establish PASS. An unexplained difference or inability to observe the effective state independently is STOP. If the OS or fixed client requires `LOCALAPPDATA` or another name, stop and version the protocol and allowlist before launch; do not add it ad hoc. No inherited owner environment, shell startup, proxy userinfo, `E2B_API_KEY`, other `*_KEY`/`*_TOKEN`, envd token or credential value is permitted in the local experiment. A later one-process envd token channel requires its own G1 release and cannot be part of G0.

The proposed **work and synthetic `USERPROFILE`** target pattern is `D:\NexusQualification\E2B-G0-LPAC\<attempt-id>\work`; it is **not an existing directory or approved final path**. The proposed **effective TEMP/TMP** target is the attempt-specific AppContainer profile's private `AC\Temp` directory returned/resolved through the documented profile mechanism, typically under `C:\Users\De Yong\AppData\Local\Packages\<moniker>\AC\Temp`. That package-private exception to the old `NexusTest` outside-owner-profile path rule must be explicitly accepted in the E2B protocol successor; it does **not** grant access to the owner's surrounding profile. Before launch, the owner must resolve exact paths and file identities, prove the work path is outside the De Yong profile, Nexus repository and existing evidence root, prove both paths have no reparse/ancestor substitution, and verify effective package isolation and only the fixed synthetic fixture. The package profile and effective TEMP/TMP must contain no copied owner secret, and the LPAC may reach no owner-profile object beyond the exact reviewed package-private objects. If the profile redirection, D: work location or ACLs cannot be verified without broader access, stop for a path or architecture decision.

Default handle policy is `bInheritHandles=FALSE` and zero inherited handles. If the reviewed fixed probe demonstrably needs standard streams, a separate exact variant may use only those stream handles through `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`; `bInheritHandles=TRUE` is then allowed **only** with that explicit list, and the controller must prevent accidental concurrent inheritable-handle creation. No token, owner credential, SDK, browser, file, socket, process or Job handle may reach the child. Trusted controller and/or OS-side observation of the **same process's effective handle state** must record source, scope and relevant inherited/open handles, distinguishing approved inherited streams from OS-opened handles. Creation attributes and this independent bounded observation must agree; the child's raw handle count or self-report cannot establish PASS. If relevant handle inheritance/open state cannot be independently verified, STOP.

## 5. Pre-execution ordering, descendants and cancellation

The future controller must complete path, ACL, image, environment, capability, handle and Job configuration checks before process creation. It creates the fixed LPAC process with `CREATE_SUSPENDED` and the exact `STARTUPINFOEX` attributes. While the primary thread remains suspended, it verifies the child token and image, assigns the child to the preconfigured Job if the chosen supported OS path did not assign it atomically, confirms Job membership and limits, and only then resumes the thread. Any creation path that permits child instructions to run before containment is established is rejected. `CREATE_SUSPENDED` alone is not Job containment.

The Job must be owner-controlled, cover the admitted process tree, disallow breakaway, impose reviewed supported resource/process-count and user-mode CPU-time limits where applicable, and support terminate/wait/readback. It does **not** itself impose a wall-clock deadline. The trusted controller enforces the predeclared monotonic wall-clock deadline: on expiry it stops dispatch, calls `TerminateJobObject` on the held Job, waits for the bound process tree and verifies no experiment process remains through owner/OS-side readback. The local probe should require no descendant; its fixed negative cases attempt direct child creation and any available brokered/alternate creation path, including WMI/COM if reachable, and require denial or verified containment. Windows Job inheritance has documented exceptions, so source-level assumptions do not pass. If a descendant escapes, cannot be enumerated, or cannot be terminated within the bound, FAIL/STOP and retain the unresolved process state.

The Job must also use a verified kill-on-last-handle-close policy with no Job handle inherited by the child or held by an uncontrolled actor. On controller exit or crash, closure of its last Job handle must terminate the contained tree; subsequent trusted owner/OS-side recovery observation must verify the final state. A controller that loses control **while still holding an open Job handle** is not protected by kill-on-last-handle-close alone: a still-operative verified deadline/termination path must act, or the required wall-clock fail-safe remains `UNKNOWN` and the experiment cannot PASS. Separately authorized local fault cases must demonstrate exit/crash and relevant loss-of-control behavior and cleanup before PASS. If last-handle custody, deadline enforcement, termination or recovery observation is uncertain, STOP/UNKNOWN; do not infer a new service or broker as a remedy.

Cancellation records separately: stop new dispatch, request `TerminateJobObject` or the approved exact equivalent, observe exit/descendants and acknowledge cleanup only after readback. The controller must retain the exact process and Job handles until the bounded result is settled. A local cancellation never implies that a later E2B API call was cancelled, that a remote guest process stopped, or that provider usage/cost was zero; those require exact Sandbox-ID reconciliation.

## 6. Owner-verifiable evidence, admission and G2 relationship

The trusted controller's bounded record must bind one attempt ID, its own identity and reviewed binary/configuration, package moniker/SID, allowed capabilities, LPAC attribute, predeclared executable/dependency bytes and the same-process loaded file/byte-basis observations, check-to-create stability evidence, exact environment-name/nonsecret-value policy **and independently observed effective environment including redirected TEMP/TMP**, handle policy **and independently observed relevant inherited/open handle state**, resolved work/TEMP paths and ACL observations, creation API outcome, the controller-held process handle, PID **plus creation time**, queried child token, Job identity/limits/membership **before resume**, resume time, fixed probe status messages, wall-clock deadline/termination and controller-failure cleanup observations. For each independent observation, record source and scope. Use a monotonic local sequence and protect the record from child modification. A PID, Security event, child-authored file or controller source hash alone is insufficient. No credential value, token value/fingerprint, raw environment dump or opaque signed URL enters evidence.

This component is a fixed qualification/data-plane client only. It may call only the predeclared envd operations against one pinned Sandbox ID after a separate release; it cannot choose arbitrary commands, URLs, providers, credentials, volumes, policy mutations, Agents, MCP, Skills, installation or task scheduling. Any move toward a general execution API requires a new architecture decision. The E2B provider, not this local client, would own the guest execution substrate. The complete Host/tool graph—including indirect and deferred paths—would still need G1 conformance before G2 dispatch.

LPAC isolation is only one prerequisite. G2 must still independently enforce task authority and mandatory budget/resource bounds **before** side effects; record reserve → dispatch → settle/reconcile → release; stop new dispatch on cancellation; preserve checkpointed accepted artifacts and unresolved effects; and reconcile ambiguous remote operations and late cost before unsafe retry. An LPAC PASS supplies no provider hard spending cap, live network-policy attestation, external-effect receipt, G2 ledger, or Host qualification. The cumulative Nexus G2-B owner ceiling remains RM5; unknown provider cost is not zero.

## 7. Falsifiable local experiment gate

This section specifies a future test, **not permission to implement or run it**. A separately accepted architecture successor, independent security review, exact source/binary/path/capability protocol and explicit owner authorization are prerequisites. The local experiment uses synthetic nonsecret data, no E2B key/envd token, no provider call/Sandbox, no untrusted payload, no repository access by the child and no G2 dispatch.

| Criterion | PASS only if | FAIL / STOP |
| --- | --- | --- |
| Controller and image | Non-elevated owner controller and one fixed reviewed image/dependency closure are verified; check-to-create stability and the suspended process's loaded main-image file identity/byte basis match the predeclared artifact, while dependencies loaded before or after resume are independently bound to that same process and reviewed bytes before their affected operation is qualified. | Wrong/mutable/unbounded image, path or DLL graph: **STOP**. Unexpected image actually started: **FAIL**; loaded bytes or dependencies cannot be independently bound: **STOP/UNKNOWN**. |
| Effective identity | Owner-held process handle binds the queried owner user SID, expected package SID, `TokenIsAppContainer`, LPAC policy, Low integrity, exact capability set and non-elevated state to the same child. | Mismatch/extra capability/elevation: **FAIL**; unavailable independent token readback: **STOP/UNKNOWN**. |
| Environment and handles | Trusted controller/OS-side observations of the same process, with source and scope recorded, show only the predeclared effective environment names/nonsecret values and actual redirected TEMP/TMP paths; relevant inherited/open handles show zero inherited handles or the exact approved streams. Child status only corroborates. | Secret/extra handle or environment name: **FAIL**; independently unverifiable effective environment or handle state: **STOP/UNKNOWN**. |
| Files, work and TEMP | Canonical paths, ACL/effective denial, fixture contents and AppContainer profile state satisfy Section 4; owner repository/evidence/profile-secret access is denied. | Owner material readable, path substituted or unapproved write: **FAIL**; partial ACL/read evidence: **STOP/UNKNOWN**. |
| Credential boundary | Fixed status-only `CredReadW` for `Nexus-E2B-G0-Control` under the verified child token returns a negative status; no secret value is materialized in evidence. | Successful read or any value disclosure: **FAIL**; ambiguous/no result: **STOP/UNKNOWN**. |
| Launch order and tree | Child is suspended until verified Job membership/limits; direct and alternate descendant/breakaway attempts are denied or remain verifiably contained. | Pre-Job execution or escaped descendant: **FAIL**; unobserved path: **STOP/UNKNOWN**. |
| Cancellation and evidence | Controller deadline termination, exact child/Job exit and no remaining experiment process are verified; bounded controller-exit/crash and relevant loss-of-control fault cases demonstrate the applicable fail-safe and trusted recovery readback; owner-controlled records correlate all facts to one process and are secret-free. | Active unexpected process or forged/mismatched record: **FAIL**; uncertain deadline enforcement, loss-of-control cleanup or attribution: **STOP/UNKNOWN**. |

Overall local `PASS` requires **every** row to pass on the same attempt. Any `FAIL` or mandatory `UNKNOWN` blocks promotion; do not retry with broader capabilities, disable LPAC, use a different executable, or substitute a child self-report. No ordinary AppContainer fallback follows an LPAC failure. Even a local `PASS` permits only owner review of a separately versioned E2B G0 proposal; it does not create or qualify a Sandbox.

## 8. Later E2B gates, rollback and change control

Before any later E2B G0, a successor protocol must rebind the account/project, current cost and hard exposure boundary, exact SDK/envd version, one-Sandbox request, actor inventory, LPAC network capability and control/data-plane split. If the later LPAC needs `internetClient` or another network capability, its exact executable/dependency identity, LPAC identity/capabilities and launch configuration must first receive separate authorization and a complete secret-free isolation qualification under the **actual network-capable configuration**. An empty-capability local PASS cannot be reused; missing or contradictory proof is STOP before G0 create, G1 review/token handoff or real E2B use of that variant. `internetClient` is broad and not an exact-host allowlist; if the fixed local client or any exposed untrusted path can address arbitrary external hosts and a hard exact-host restriction is mandatory, this alternative stops unless a separately accepted enforcement mechanism is demonstrated. Do not silently add a local proxy, firewall service, broader token or custom broker. A later G1 release remains distinct, and the first untrusted guest execution remains separately unauthorized here.

For a local experiment, rollback terminates the exact Job/process tree, verifies no active child, removes only the experiment-created AppContainer profile and synthetic work/TEMP objects when safe, and preserves status-only failure evidence. A failed removal, orphan, secret exposure, uncontrolled network route, or unprovable launch keeps the result `UNKNOWN`/FAIL and the architecture on HOLD. Do not delete historical evidence or silently switch to the accepted `NexusTest` mode.

This requires a **new versioned architecture alternative decision and separate owner acceptance**, not an in-place edit of the accepted HOLD. A future accepted successor would explicitly supersede `docs/nexus-pre-g2-trusted-launch-architecture-decision-v1.md` **Section 3** (the conditional `NexusTest` launcher boundary), **Sections 4–7** (its primary-token source, conditional launch contract, Option A experiment gate and rollback) **only for Alternative 3**; its **Sections 1 and 8** and `docs/nexus-pre-g2-trusted-launch-architecture-acceptance-v1.md` would need an explicit status/supersession cross-reference. The accepted Option A HOLD remains in force for the separate-account route. Even acceptance of the new architecture would not by itself replace Option D with a qualified Host or permit implementation; that requires later, separately authorized and observed gates.

`docs/nexus-pre-g2-architecture-addendum-v1.md` A0–A6 and `docs/nexus-pre-g2-architecture-acceptance-v1.md` need **no textual successor under this proposal**: their default-deny and qualified-Host requirements remain controlling. If a later design cannot comply, it must request an explicit amended version and owner re-acceptance before proceeding. The E2B protocol needs a versioned successor to `README.md` and at least `03-restricted-executor.md`, `05-credential-isolation.md`, `06-configuration-binding.md`, `07-trusted-observation.md`, `08-release-boundary.md`, `09-negative-tests.md`, `10-toctou.md`, `12-success-criteria.md`, `13-stop-conditions.md`, `14-owner-authorization.md` and `15-prior-art.md`; see `docs/nexus-e2b-appcontainer-protocol-successor-proposal-v1.md`. Its untouched sections must be rechecked for cross-reference consistency. Frozen Roadmap, G1 and R2/R4/R5 artifacts are not edited.

## 9. Documentary review disposition and sources

**Architecture:** a concrete documented same-owner AppContainer launch mechanism exists in principle; availability, isolation and E2B compatibility on this Host remain `UNKNOWN`. **Security:** credential denial, code-load closure, effective handles/environment, broad `internetClient` reach and descendant escape remain mandatory open questions. **Testing:** no local process, AppContainer profile, ACL change, probe, E2B call or G2 test has occurred. This proposal is not a qualification receipt or an approval request for automatic execution.
