## 1. Decision, evidence and finite scope

Propose moving creation and continuous debug observation of each fixed watchdog from the controller to the **existing Owner Release Verifier**. The verifier directly creates that watchdog under its own debug connection, binds its actual loaded image and relevant dependencies from creation, and keeps that connection through cleanup and exit. It continues observing the corresponding fixed controller. The controller remains the LPAC creator/observer and Job owner; the watchdog remains the independent controller-loss/deadline cleanup component. No observer executable, account or privilege is added.

This resolves one documented responsibility conflict, conditionally. The accepted verifier specification says **“Verifier watches only controller.”** The accepted Evidence Successor Protocol preserves that role, while requiring actual watchdog provenance and independent cleanup. The preserved implementation checkpoint reports `NEW_ARCHITECTURE_REQUIRED`: controller-to-verifier detach/attach can leave a suspended watchdog outside either debugger's fail-safe when verifier failure kills the controller. Direct creation under one retained verifier debug connection removes that proposed handoff interval by design; it does not prove the resulting Windows behavior or LPAC qualification.

## 3. Fixed trust boundary and creation order

The one reviewed verifier is launched by the owner through the accepted external owner path. It proves its own De Yong interactive identity, non-elevation, no AppContainer and no outer Job; a shell opened from the UI is not proof. It accepts only the existing literal activation marker. No executable/path/PID/case/provider/capability/environment/deadline selection is exposed to the caller. A future successor freezes exactly one controller and one corresponding watchdog per existing case, plus the already accepted case-03 recovery image. Historical filenames identify roles, not permission to execute current or staged bytes.

Required order for each case:

1. Verify protected package/ancestor objects, exact reviewed bytes/manifest, host/CI anchors and unused attempt/evidence/Job identities. Establish the verifier's finite abort policy before creating any debuggee.
2. The same verifier debug thread creates the fixed controller suspended under `DEBUG_ONLY_THIS_PROCESS`, fresh Unicode allowlisted environment and no inherited handles. Bind the returned process/thread objects, PID plus creation time, actual main image and independently observed process facts before application release. Keep its debug connection throughout.
3. Permit only verified controller setup to reach a fixed, reviewed **pre-watchdog barrier before Job/LPAC process creation**. A controller record is a request for the next fixed step, never authority to choose an executable or PID. Verifier-held identity and observed ordering must independently corroborate the barrier; a missing or bypassed barrier STOPs. Any synthetic profile/files already created remain inventoried cleanup obligations.
4. The verifier directly creates that case's one fixed watchdog suspended and debugged on the same debug thread. There is no interval in which a created watchdog is intentionally detached or awaits attachment by another observer. Record the creation result before other release work; ambiguous creation is STOP/reconcile, never a replacement watchdog.
5. Independently validate watchdog main image, observable initial dependencies, owner/token/no-Job, exact effective inputs and relevant handles. Release only through verified loader/event gates, then require independently corroborated live readiness and flushed owner-only records before allowing the controller to create its Job or any LPAC process. The verifier continues watching both subjects and gates relevant late loads before their code affects qualification.
6. The controller creates/validates the original constrained Job. Bind its actual object, protected rights and deadline to the same case/controller/watchdog; a name or ready line alone cannot establish this. Before LPAC creation, prove the live watchdog can perform the required cleanup against that exact Job independently of controller progress. The controller creates LPAC suspended under its own retained debug connection; required LPAC validation and verified Job assignment precede application execution.
7. Keep both verifier debug connections until their respective exits are observed and reconciled. A controller exit does not end watchdog observation. Case-03 recovery remains limited to its exact existing role/bytes and starts only after required tree/watchdog cleanup. No next case starts without the original full prior-case cleanup/adjudication gates.

This is a conditional ordering contract, not an implementation recipe or proof that the fixed barrier/debug interactions work. If same-thread event handling, startup ordering, Job binding or nested debugging cannot satisfy it, STOP; do not revert to handoff or detach.

## 5. Failure and cleanup contract

### 5.1 Three distinct mechanisms

**Controller-loss independence:** with the verifier alive and its event pump responsive, watchdog execution/clock/cleanup does not require a controller thread, controller debug port, controller-owned readiness handle or controller-written final receipt to progress. The watchdog remains debugged by the verifier, not by the failed controller. It must survive controller crash/stall long enough to terminate and verify the contained tree at the fixed deadline. This is operational independence from the controller, not independence from every trusted component or Windows.

**Verifier-loss termination:** retain default debug kill-on-exit from the first creation, and positively establish the required TRUE policy on the owning debug thread once a connection exists; never set FALSE. No debuggee is intentionally detached. When that thread/process exits, the intended fail-safe is termination of both direct debuggees; LPAC's controller-owned retained debug connection and `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` cover the contained tree. The last Job handle must close: inventory every authorized holder (only fixed trusted components), prevent LPAC/unrelated inheritance or duplication and reconcile holder exits. Unexpected debug-thread exit while other verifier threads remain alive must trigger whole-verifier termination within the fixed abort bound; a surviving verifier must not retain a Job handle that defeats last-close cleanup. Merely closing a process handle does not terminate its process. These mechanisms require combined fault evidence, including suspended watchdog and LPAC create-to-Job-assignment windows; API contracts alone cannot PASS.

**Observer stalls:** a debug event pauses the affected watchdog and may postpone its user-mode deadline. Do not claim it keeps running through an outstanding event, or that one event pauses every subject. The existing verifier must have a fixed bounded event-service/abort deadline and an in-process fail-safe, independent of progress of its debug/event-observation thread, that terminates the verifier if that thread loses progress; this activates the retained kernel kill-on-exit path. The fail-safe is only a fixed timer/termination function inside this same verifier, not another observer/verifier, service or generic health framework. It makes no provenance/PASS decisions and must not wait on the observer's locks, receipt flushes or target operations before terminating the whole verifier. Its exact implementation and byte/dependency identity require later review. No deadline is extended by debugging pauses. Controller/watchdog timers remain as accepted; a Job Object does not supply wall-clock enforcement. If the abort path can block on the same failing observer, if required termination cannot occur within the existing reviewed bounds, or if suspension can defeat all cleanup, keep UNKNOWN/HOLD and seek a new bounded decision. Do not assume absence of observer events means health.

### 5.2 Mandatory failure matrix

All rows stop further release/cases on an unexpected failure; an expected case-03 controller crash or case-04 stall can satisfy only its specifically exercised criterion after complete independent evidence. Termination request/exit code is never cleanup proof. A surviving verifier performs bounded termination/waits against **held, bound objects**, drains events only as needed for termination, and reconciles Job/descendants. If the verifier is gone, later owner/OS readback must establish every original process's exit and zero live tree; no new observer process is automatically authorized.

| Case | Required action and fail-safe | Evidence / disposition |
| --- | --- | --- |
| A. Verifier fails before controller creation | No controller/watchdog/LPAC may have been created. Stop; preserve any already written owner evidence. | Confirm creation count and absence; missing evidence UNKNOWN. No PASS or automatic resume. |
| B. Verifier fails after controller creation, before watchdog creation | Controller is suspended or at the pre-watchdog barrier; no Job/LPAC process creation is allowed. | D. Verifier fails after watchdog release, before controller failure | Kill-on-exit terminates controller and watchdog. Controller's debug connection and final-close Job fail-safe must terminate any suspended/assigned/running LPAC tree. | Verify all original identities, Job handle closure/zero-live tree, no escaped descendant. | E. Controller fails while verifier alive | Keep verifier/watchdog connection and late-load gates alive through watchdog cleanup. Cleanup invariants apply to verifier, controller, watchdog, recovery and every LPAC descendant. On abort, prefer explicit termination of the exact constrained Job when a trusted bound handle is available, then wait for every bound process; terminate direct debuggees as required to close their Job handles. Kernel fail-safe is backup, not a receipt. Process exit/debug-exit alone does not prove no escaped descendant. Require trusted Job active-zero evidence where the object remains observable and owner/OS-side reconciliation of original process identities and all created descendants; absence of the Job after last close needs corroborated zero-live tree evidence. Profile/synthetic-file removal waits until positive process cleanup and is limited to this attempt's inventoried new objects. Preserve evidence and historical packages. Unresolved cleanup prohibits later cases and is escalated with exact object identities; STOP never licenses abandonment or deleting away uncertainty.

## 6. Acceptance, implementation gates and falsifiers

Document acceptance would replace only §2's role/lifecycle clauses. It is **not** an implementation authorization, approval of staging, package promotion or runtime release. Further work needs separately valid bounded implementation authority, an exact reviewed successor specification/source/build/manifest and protected package, then separate exact-byte owner authorization for any safe feasibility test or qualification execution. No historical G0/G1, local case or interrupted implementation authorization silently overrides this new acceptance gate.

Before any package promotion, independent static/adversarial review must find: closed fixed subject table; same-thread creation/retained debug ownership; no detach/arbitrary attach or FALSE kill-on-exit; independently checked pre-watchdog barrier and ready-before-child order; effective inputs/handles; actual-load/event ordering; bounded observation-thread fail-safe; complete Job-handle custody and create-to-assignment loss cleanup. Test instructions must predeclare fault points A–I, exact binaries, bounds and outcome records. Safe nonqualification tests, if separately authorized, use fixed synthetic subjects with no LPAC/secrets/network and test these same OS mechanisms; they cannot establish actual LPAC PASS.

The later exact four-case qualification must demonstrate controller-loss watchdog survival/late loads, verifier/debug-thread loss at all relevant windows, event-pump stall/abort, watchdog failure, negative containment/handles/provenance, deadline/cleanup races and owner-only readback. Fault assertions are bounded subtests supporting the existing four scenarios, not a fifth scenario or automatic permission to rerun them. Every relevant executable load must be gated through the watchdog's final cleanup operation and exit. If a required event/exception/handle path cannot be classified, STOP rather than consume it as harmless. No fault test or normal successful exit alone is HQ1–HQ5 PASS.

**Reject/abandon this candidate** if it requires privileges beyond the existing non-elevated same-owner process/token/Job/debug rights, `SeDebugPrivilege` elevation, password/token transfer, a privileged service/broker, Task Scheduler, outer-Job breakaway, NexusTest/Option A fallback, network, a generic observer surface, dropped provenance, unbounded observer pause, or unverified/orphan cleanup. Preserve the rejected package/evidence and request a precisely scoped new architecture decision; do not silently detach, add a verifier or weaken the protocol.
