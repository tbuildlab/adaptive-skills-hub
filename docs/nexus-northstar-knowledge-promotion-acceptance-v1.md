## 3. Accepted core principles and evidence semantics

### Core principles

- **CP1 — Advisory authority:** advisors can propose findings; superior platform/user/project rules determine scope and disposition. Advice, metadata and generated plans never grant permissions. This consolidates the existing [V1.2 Rules Engine](v1.2-product-architecture-spec.md), not a new issuer.
- **CP2 — Truthfulness:** in public/user-facing claims, distinguish evidenced facts, source-supplied facts, inference, fiction/demo and unknowns. Do not invent ratings, testimonials, certifications, partners, years, contacts, metrics or delivery. A polished artifact is not business proof. Project-specific style bans are excluded.
- **CP3 — Mode/effect clarity:** provider-backed demonstrations identify actual mode, active/deferred effects and handling of invalid/missing mode. Future real activation requires its own authority and evidence. Northstar's fallback-to-demo is not prescribed.
- **CP4 — Effect-aware recovery:** for external effects, local timeout, abort, transport loss or a UI response does not settle remote execution, cancellation, persistence or cost. Unknown outcomes require risk-appropriate observation/reconciliation before an unsafe retry or success claim. This preserves [Pre-G2 A2](nexus-pre-g2-architecture-addendum-v1.md); it does not authorize execution or alter G2 hard-bound requirements.
- **CP5 — Subject/freshness binding:** evidence names subject, relevant config, governing criteria, source, coverage and time. Changes invalidate affected current conclusions; historic records retain their actual scope. This consolidates [Slice 3B](nexus-post-r5-runtime-integration-slice3b.md) exact-subject checks and Pre-G2 A4, without a new memory service.

### Evidence semantics

Each ES item is ACCEPT_AS_EVIDENCE_SEMANTIC for its stated observation scope:

- **ES1:** UNKNOWN stays UNKNOWN; UNVERIFIED needs new evidence before upgrade. Absence of evidence is not evidence of absence. Owner acceptance of wording/disposition cannot turn a missing mandatory security fact into PASS.
- **ES2:** requested/configured/selected state is distinct from observed applied state/effect. Credential presence is not execution. UI observation is not automatically backend-effect or non-persistence evidence. Exact effect correlation and observation coverage remain necessary for the claim being made.
- **ES3:** a generated report establishes report production, not execution of its underlying checks. Hashes establish bytes, not truth/approval/authority. Reconstructed, source-reported and newly observed evidence remain separately attributed.
- **ES4:** build success is distinct from release success; release status is distinct from live-behavior verification. No implicit numeric performance score, backend effect or security certification.
- **ES5:** §4 accepts the four independent capability observations; existing success, validation, approval and eligibility details remain distinct.
- **ES6:** §5 accepts five independent deployment facts when the corresponding stages exist; missing linkage is UNKNOWN.

All accepted semantics are evidence interpretation/governance only. Existing strict schemas and evidence grades are preserved; no automatic transition, serialized enum change, authority expansion or evidentiary waiver is implemented.

## 4. Accepted four-dimensional capability model

Accept [capability observation model v1](nexus-capability-state-model-v1.md), §§1-3, with §4 retained as historical examples and §5's pending status resolved only by this acceptance. Each dimension requires its own environment/context/time/source/operation binding; YES, NO, UNKNOWN and reasoned NOT APPLICABLE are documentary observations, not new runtime lifecycle enums.

| Dimension / classification | Accepted meaning and evidence obligation |
|---|---|
| INSTALLED — ACCEPT_AS_EVIDENCE_SEMANTIC | Exact capability/tool/package exists in the relevant environment. Scoped identity/version/presence observation only; no callability/use inference |
| CALLABLE — ACCEPT_AS_EVIDENCE_SEMANTIC | Valid reachable invocation path exists for the exact operation under the relevant permitted context and prerequisites. Scope/time/Host/path evidence; discovery alone is insufficient and this fact grants no authority |
| EXECUTED — ACCEPT_AS_EVIDENCE_SEMANTIC | Bound invocation/trace/receipt proves a relevant attempt with actor, operation, subject/time and outcome. A failed attempt can be executed; it need not have applied output |
| APPLIED — ACCEPT_AS_EVIDENCE_SEMANTIC | Evidence correlates identified invocation/output/effect to the artifact/state/result being accepted, with exact subject/configuration and acceptance reference. Mere output existence or similar resulting code is insufficient |

INSTALLED does not prove CALLABLE; CALLABLE does not prove EXECUTED; EXECUTED does not prove APPLIED. These are independent dimensions, not sequential gates or required unequal values. A remote/native capability can be callable without a local installation; a later installation cannot prove historical execution. Lack of evidence is UNKNOWN, not observed NO.

Four dimensions are sufficient for this accepted reporting purpose. No additional state is added. Existing R4/R5 traces, G1 profiles/conformance, capability lifecycle/availability and Slice 3C approval separation remain authoritative in their own scope. This model supplements them and cannot replace a Host receipt or infer approval, eligibility, validation, routability or effect authority.

## 6. Accepted applicability semantics; no engine

The following lightweight documentary decision model is ACCEPT_AS_EVIDENCE_SEMANTIC. It adds no policy language, automatic planner, tracker or executor.

**Project/task context -> capability/risk/delivery profile -> applicability evaluation -> only relevant gate subchecks -> scoped evidence -> PASS / FAIL / UNKNOWN / NOT APPLICABLE.** The every-project-runs-every-gate model is rejected.

Consider only relevant inputs: artifact type, UI/accessibility surface, network/API, public exposure, SEO, deployment target, PII/secrets, provider integration, external effects, payment/cost, persistence, demo/production mode and risk. Values are source-bound observations, not new permission assertions. Missing a relevant profile fact is not evidence it is absent.

A minimal assessment names task/subject/configuration/criteria, gate and applicable subcheck, governing requirement, profile basis, applicability class/reason, required evidence and current outcome/gap. No new JSON schema, runtime storage or enumerated state machine is introduced.

| Applicability | Accepted rule |
|---|---|
| REQUIRED | Actual scope, accepted criterion or risk mandates this property. Missing evidence -> UNKNOWN; observed contradiction/proven missing prerequisite -> FAIL as defined by the check. Never missing -> PASS |
| OPTIONAL | Adds justified decision value but is not a superior mandatory requirement. If unperformed, record not performed/UNKNOWN; no fabricated PASS or acceptance coverage |
| NOT_APPLICABLE | Positive scoped reason excludes the surface/property. Missing tools, evidence, authority or convenience are not exclusion reasons. Corresponding documentary result is NOT APPLICABLE, never PASS |
| DEFERRED | Relevant work is pending a prerequisite/separate authorization or explicit scope change. Record reason/dependency and gap; it does not establish satisfaction or authorize the deferred action |

Applicability and check result are distinct. OPTIONAL/NOT_APPLICABLE/DEFERRED cannot weaken an existing REQUIRED property. A required deferred/unknown/failed item prevents the related acceptance, release, provider activation or unsafe retry. Ambiguous security-relevant applicability remains pending/UNKNOWN, cannot be downgraded to optional/non-applicable, and blocks the affected claim/action until resolved.

A justified optional unresolved diagnostic may coexist with narrowly scoped acceptance only when no mandatory premise depends on it and the omission/impact/disposition is explicit; the diagnostic remains UNKNOWN. Different gate families may select different subchecks. Gate F requires evidence for the actual closure criteria, not every example in the catalog. Relevant secret/PII document handling still applies even when API/network checks do not.

Examples are semantic cases, not executed tests: a secret-free non-public local Markdown task has no web keyboard/API/SEO/deployment checks, but its declared document integrity/acceptance checks remain required; an interactive public site selects relevant content/keyboard/live/release checks; backend-only provider writes select input/data/effect checks without design/menu checks. A demo accepting form data still has PII boundaries; demo mode does not exempt it.
