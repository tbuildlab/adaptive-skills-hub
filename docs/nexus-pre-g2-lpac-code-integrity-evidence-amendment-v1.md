## 1. Conclusion and exact scope

**B. EXACT CI POLICY IDENTITY IS REPLACEABLE EVIDENCE.**

Complete current per-policy Code Integrity (CI) identifiers, versions and enforcement enumeration is a presently binding evidence gate, but is not itself an HQ1–HQ5 security property. For this exact local configuration, a bounded replacement can preserve the property through independent effective-state, custody, actual-load, unchanged-security execution and failure evidence. This is not a conclusion that DeviceGuard status 2, a successful launch, a signature or an unknown policy identity is sufficient.

The scope is only the accepted non-elevated De Yong, empty-capability, synthetic, secret-free, fixed four-scenario local LPAC configuration and its fixed verifier/controller/watchdog/recovery/probe/canary roles. The preserved V3 manifest is `C359EE0BCA2480A25454D7C0AD5A7544D47BE57428C9008C17FC383519884F4B`; repository baseline is `725ca39bbdb1a82902f02da0a26b5a614da96b35` on `nexus-v2-g2-development`. A separately reviewed exact implementation/package successor would be required to use this proposal. No existing sealed package is reinterpreted or modified.

Until explicit owner acceptance, all existing CI STOP gates remain binding. Current CI is **UNKNOWN/STOP**; Scenario 01–04 **NOT RUN**; HQ1–HQ5 **NOT PASS**; Positive Host Binding **ABSENT**; G2 **HOLD**. Option D remains current and Option A remains HOLD. No earlier execution authorization transfers.

| Class | Requirement and purpose |

Actual Nexus-loaded code is independently bound to held protected reviewed bytes before relevant execution; actual Windows system images are bound to the accepted protected physical-image/build/hash/trust/loader TCB. The threat is unauthorized or substituted executable code, weakened effective enforcement, or an evaded block producing false provenance/isolation evidence. The security property is not the spelling of a GUID. An ID and version are useful correlation, but without an approved semantic/content baseline and actual effective state they do not establish a sufficiently restrictive policy. The accepted local artifacts name no approved full CI rule-set baseline whose restrictive semantics substitute for Nexus's own fixed admission/provenance rules.

Nexus governance/task-policy identity remains mandatory under G1 and Pre-G2 A2. Its full-policy binding must not be confused with enumeration of every Windows CI policy. This proposal does not exempt task grants, capability/configuration identity, policy intersection, pre-effect default deny or mandatory unknowns.

## 4. Threat analysis and ten adversarial questions

| Question | Analysis and consequence |
| --- | --- |
| 1. What attack becomes possible when exact IDs are unknown? | Loss of inventory can hide a rule-only weakening or policy replacement that an approved content/state baseline could detect. It does not directly grant LPAC authority or permit code through the independently closed Nexus boundary. No claim of arbitrary policy-drift detection follows from the replacement. |
| 2. Can a weaker policy still report enforcement? | Yes. An enforced policy can allow much more code; supplemental rules or an AllowAll-style policy can change admission semantics. Aggregate enforcement is insufficient. Untrusted local subjects must have neither policy-mutation authority nor a writable executable/input path; fixed code and actual-load denial remain independent mandatory controls. Owner/SYSTEM/kernel compromise remains outside the accepted threat model. |
| 3. Does successful exact-byte launch independently prove enforcement? | It proves that the exact operation was admitted through that path, not that CI was restrictive or denied other code. Combine OS effective-state evidence, normal loader/path execution, independently reviewed no-mutation behavior and actual loaded provenance. A block remains STOP. No special exemption is allowed. |
| 4. Do provenance checks compensate? | They directly address executable substitution even if Windows CI would admit the substitute. They do not prove Windows policy strictness, kernel integrity or arbitrary runtime safety. Every relevant load must retain the accepted pre-instruction/pre-effect gates, physical identity and byte/trust basis; unknown closure STOPs. |
| 5. Does system-module TCB provenance depend on a particular ID? | Not in this accepted local contract. It depends on the same actual mapping's protected physical Windows image, pinned build/hash/version, applicable positive Microsoft signature/catalog trust, effective CI basis and the explicitly trusted Windows loader/kernel. A future reliance on a specific CI rule would require separate accepted policy identity/content evidence. |
| 6. Are IDs only reproducibility metadata? | They provide useful security correlation and reproducibility, not an intrinsic proof of allowed-code semantics. Preserve obtainable metadata and its scope. Reproducibility of this local claim binds exact code, OS anchors, launch configuration, required effective-state facts, actual effects and residual unknowns; it does not claim replication of the entire machine policy set. |
| 7. Does replacement weaken an accepted invariant? | Deleting the gate without replacement would. The proposed combination retains the HQ security properties and expressly changes one evidence contract. It accepts less administrative inventory assurance and explicitly does not claim to detect all rule-only policy drift. It is valid only while no local security claim depends on those missing semantics. |
| 8. Does the old gate create an ordinary-owner dependency? | On this host it currently cannot be satisfied using validated non-elevated sources. This is feasibility evidence, not a reason to relax security. Windows-wide impossibility or fundamental elevation necessity is not established. |
| 9. Is a bounded successor defensible? | Yes, conditionally on every §5 requirement being independently observed. CI status 2 alone, retrospective logs alone and launch alone are rejected. The required new combination remains untested and STOPs on missing evidence. |
| 10. Does it generalize? | No. Only the exact local empty-capability qualification boundary is covered. Network LPAC, E2B, HQ6, production execution, arbitrary code, different CI-dependent admission or a changed threat model require their own qualification/decisions. |

The accepted TCB excludes malicious owner/SYSTEM/kernel, not a merely inconvenient missing observation at the Nexus-to-Windows boundary. Known policy weakening, any observed contradictory enforcement, an untrusted policy/configuration writer, unverified bootstrap custody or incomplete actual-load evidence cannot be excused using that exclusion. Trusted Windows policy lifecycle inside the TCB is not independently re-attested by this proposal. Hidden rule-only changes are not claimed detectable; every known/observed relevant change invalidates affected observations even when IDs are unavailable. No historical result is reused as a new attempt's runtime PASS.

## 5. Mandatory replacement evidence — conjunctive, not alternatives

Every row is required. Windows query surfaces are independent of the LPAC subject, not independent of the trusted Windows kernel. A trusted component's bound OS-query result is evidence; a child assertion, caller-supplied success flag or fabricated fixture is not.

| Gate | Required source, timing and scope | Failure rule |
| --- | --- | --- |
| CI1 — finite custody and host binding | Owner-side protected physical package/ancestor/manifest verification; exact reviewed roles/dependency basis; owner SID, non-elevation, interactive origin and no outer Job on the actual required components; current pinned OS/ntdll/PDB. Bind attempt, package digest, case, held process/PID/creation time, source and ordered observation time. | Unstable/writable/substituted input is FAIL; unavailable custody, binding or anchor is UNKNOWN/STOP. |
| CI2 — effective enforcement | Fresh OS-side `Win32_DeviceGuard` and native `SystemCodeIntegrityInformation` evidence agree on required kernel/user-mode enforcement. Record query outcomes, raw native bitmask and interpretation. Native kernel/user-mode enable bits `0x01` and `0x04` must be set. Retain rejection of test-signing, UMCI audit, test/preproduction CI build, kernel-debug CI exception and HVCI audit; additionally reject `CODEINTEGRITY_OPTION_UMCI_EXCLUSIONPATHS_ENABLED`. The forbidden mask is `0x08FA`, including the exclusion-path bit `0x10`: the replacement may not hide a path-based CI exemption. Preserve the observed HVCI/VBS baseline: native HVCI enable `0x0400`, WMI kernel/user-mode enforcement both 2, VBS status 2 and memory-integrity service configured/running. Do not lower these to facilitate launch. Security-relevant unclassified or contradictory effective state STOPs. | Missing query, malformed result, missing required bit or unknown relevant interpretation is UNKNOWN/STOP; positive disabled/audit/exempt/bypassed state is FAIL/STOP. Status 2 alone cannot satisfy this gate. |
| CI3 — freshness and no qualification bypass | Owner-side aggregate readback must be taken within five minutes before the specifically authorized activation and within five minutes after completion/abort, with the same boot/build/owner binding. Native readback in the fixed verifier must precede downstream creation, bracket each case's creation/release and final cleanup, and cover recovery/watchdog cleanup after controller loss. Keep raw observations, not only a final boolean. The fixed reviewed source/launch configuration contains no machine CI/Application Control/Device Guard mutation or weakening, special CI exemption, alternative controller account, privileged launch, opportunistic signing/rebuild, breakaway or fallback. Existing constrained LPAC/profile/Job/synthetic-object setup remains governed by its unchanged protocol and is not a machine-policy exemption. Preserve known intervention/block records and owner action history as corroboration. | No historical WMI result supplies freshness. Failed/late/missing required readback, observed drift or contradictory action/source evidence STOPs further release. If verifier loss prevents a required receipt, retain UNKNOWN for owner/OS reconciliation; do not infer unchanged state from clean exits. |
| CI4 — real normal-path admission | Separately authorized exact bytes use normal Windows process/image loading on the accepted non-elevated owner path, with the original suspended/debug/Job ordering. Record the actual creation/load outcome and normal code path. Neither a file's presence nor no block event proves successful launch. Verifier bootstrap rests explicitly on owner-reviewed protected bytes and Windows loader/CI TCB, never self-reported admission. | Actual refusal STOPs. No sign/rebuild/substitute, allow rule, security toggle, special bypass or elevated route may rescue the attempt. Required launch outcomes remain UNKNOWN until observed. |
| CI5 — actual-loaded provenance | Nexus-controlled code retains held immutable file objects, physical IDs, same-process creation/load mappings, reviewed executable-byte comparison and dependency/event ordering. Windows TCB modules retain actual same-process physical-image/mapping identity, protected canonical location, pinned build/file/version/hash and positive applicable Microsoft signature/catalog trust under the accepted bounded rule. Null/unresolved handles, unexpected writable paths, unexplained Nexus-byte mismatch or unclassified relevant edges do not fall through to CI acceptance. | Substitution is FAIL. Missing provenance, trust, timing or actual dependency closure is UNKNOWN/STOP, even when CI admits execution. |
| CI6 — real boundary consequences | All accepted LPAC identity/capability, environment/TEMP/workdir, security-relevant handle, owner-resource denial, descendant/breakaway/alternate-creation, Job/watchdog/deadline/controller/verifier-loss, cancellation/cleanup/recovery and receipt-integrity tests remain mandatory within the four original sequential scenarios. | No static test or CI observation marks these runtime properties PASS. Any relevant negative not detected or uncontained effect is FAIL; missing/ambiguous observations STOP. |
| CI7 — owner adjudication and limits | The protected records bind the same attempt/package/case/process/effect; independently adjudicate required before/during/after evidence and zero-live cleanup. Record unavailable complete policy metadata explicitly as UNKNOWN, separate from the bounded effective-enforcement observation. Retain obtainable IDs/versions/hashes with source, time and coverage; contradiction relevant to the gates STOPs. | No renaming policy-identity UNKNOWN to identity PASS. A bounded local claim is permitted only after all mandatory evidence and tests pass. No enterprise policy equivalence, all-policy strictness, complete policy-drift detection, network/E2B or complete Host claim follows. |

Five-minute owner-query windows are maximum evidence ages, not process deadlines or permission for an extra runtime observer. Original shorter controller/watchdog/observer bounds remain unchanged. The implementation must demonstrate bounded source availability, ordering and protected receipts using the existing finite roles; no general collector/service or new privileged code is approved. If this composition cannot work at the required timing, STOP for owner/architecture review rather than broadening infrastructure.

The native query is already used in the V3 fixed host-state helper, but current source does not reject the exclusion-path bit. Repeated/bracketed native and owner-side evidence is not established by the current package either. These are concrete future conformance corrections, not facts this document claims to have implemented. No V3 binary or frozen artifact is edited.
