## 2. Exact owner-submission message

The text between the following fences is the complete message to submit to OpenAI support/developer/platform personnel. It requests documentation only and neither asks them to start resources nor grants Nexus permission to do so.

```text
Subject: Agents API openai_hosted — six bounded-experiment safety contract clarifications

We are evaluating the OpenAI Agents API with its managed Codex harness and an openai_hosted sandbox. No experiment is running. We need authoritative supported semantics before requesting owner authorization for a bounded qualification experiment.

Candidate scope: one new small sandbox/session, network.access disabled, one fixed model and synthetic input, delegation disabled, no environment template, setup commands, added packages, MCP, function tools, web/computer-use tools, skills, plugins, vaults or customer secrets. Intrinsic shell/model/harness operations remain in scope. No production workload or external writes are proposed. If optional-tool omission leaves a service-side capability enabled, identify the supported explicit disablement needed; do not assume a prompt closes it.

Please answer the following six contract questions for this exact hosted mode. For each, cite the applicable official API/documentation, supported version and scope, distinguish hard enforcement from best effort, and give quantitative maxima where requested. If no supported bound exists, please state that explicitly. No account access, execution, credentials or internal implementation secrets are requested.

1. Configuration interval: What supported mutation/permission contract keeps security-relevant environment, network, capability, input and credential configuration fixed throughout an admitted turn, including other project actors and live file APIs? Ordinary admitted workload writes are not configuration mutation. We already recognize documented later-turn model-setting updates; please specify the uncovered mutation surfaces and the enforceable no-change interval or equivalent ordering barrier.

2. Network scope: What is the complete hard deny scope and exception set of network.access disabled for the sandbox and all descendants (IPv4/IPv6, DNS, redirects, private/link-local/metadata destinations and alternate channels), and which intrinsic harness/service connections remain outside it? This scope must justify the exact no-external-effect profile; optional remote tools are excluded as above.

3. Whole-unit containment: What finite, non-workload-relaxable resource and maximum active-lifetime envelope covers the hosted unit and all descendants/background work, including continuous activity, keep-alives and loss of the application controller? Please identify the actual CPU/memory/storage/process/output bounds or enforced nonapplicability, extension/reset rules, enforcing layer and ultimate termination fallback. An inactivity timeout or client timeout alone is insufficient.

4. Managed-loop containment: What supported hard root-agent/session bound (including any session_budget_exceeded budget) covers cumulative model calls, internal retries, reasoning/output tokens and intrinsic tool steps? Please provide the setting or service default, units, scope, maximum excess and termination consequence. A different hard total envelope is sufficient if it explicitly contains all these drivers; delegation concurrency alone is insufficient.

5. All-in financial maximum: What supported billing-and-cutoff contract permits a finite conservative amount before dispatch for this mode, including model/cache usage, containers, retained files/artifacts/storage, internal retries and failure/cleanup charges? Please bind billing-increment eligibility and provide numeric worst-case propagation/excess/residual bounds for any proposed session or project/organization cutoff, covering already-running work. We recognize documented hard monthly spend limits; an unspecified small excess, rate table or usage counter is not an all-in upper bound.

6. Stop/failure persistence: Do the Q3 work and Q5 accrual envelopes continue to hold through cancellation, deletion, lost acknowledgements and controller/transport failure, until ultimate cessation and settled charges? Please state the supported survival/termination/accrual contract and identify authoritative observation sources distinguishing request/ack, terminal execution, physical cleanup and billing settlement. Exact cancellation/cleanup latency and observation coverage can be measured later inside an already-safe envelope; API removal alone is not cessation or settlement.

Please return any restrictions, exclusions or unsupported facts explicitly. One documented equivalent composition may answer multiple questions, but must preserve the full scope above. We are not requesting a qualification run or an assurance based only on typical observed behavior.
```
