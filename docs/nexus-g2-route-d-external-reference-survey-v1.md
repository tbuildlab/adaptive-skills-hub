## 2. Firecracker: VMM plus protected Host lifecycle, not automatic P5/P7

FC01: one Host Firecracker process hosts one microVM, with API/VMM/vCPU threads and KVM/hardware reliance. Host TAP/backing files and the API remain outside guest trust; device rate controls are not complete egress policy. Guest shutdown, pause, VMM exit and deletion of backing objects are distinct. Guest code can influence packet/block/serial/log traffic; it must never reach control socket or owner credentials. The privileged owner prepares networking/images/Host restrictions; a separate lifecycle owner must manage the process.

FC02/FC05: jailer is specifically for matching static Firecracker, sets up restricted root/UID/GID/cgroups/netns and executes VMM after privileged preparation; daemon mode detaches and changes stdio. It is not a generic launcher to adapt to arbitrary binaries. A concrete source trap: Env::new with v2/no cgroup arguments checks whether a parent path exists before moving; if absent it proceeds without that move. A future wrapper must prevalidate and independently read actual placement/limits BEFORE InstanceStart. Neither UID separation nor a requested cgroup proves applied ceilings. Pin UID, KVM/device access, root/image/API paths and inherited FDs; deny guest/control-plane mutation.

FC03: Host/kernel/microcode patching, bounded log/serial handling and external detection of unresponsive VMMs are production responsibilities. A VMM killed by Host SIGKILL is not a numerical ultimate termination guarantee for every Host fault. Controller/overwatch loss can leave a running VMM; the checked source set supplies no immutable total-lifetime/fault envelope on its own. Host crash stops ordinary compute, but objects and uncertain effects survive. FC04 snapshots introduce memory/state/backing-file custody and pause/restore semantics, not a Nexus checkpoint/authority restore. Initial deterministic profile should exclude snapshot/restore/MMDS/extra devices unless separately justified. REUSE VMM/jailer; ADAPT protected supervisor/image/device/evidence integration; REJECT arbitrary jailer use, uncontrolled daemonization/recreation and snapshot reset of grants. Actual P5/P7/HQ remain UNKNOWN.

## 3. Kata: two-level resource and lifecycle composition

KA05/KA03: Host shim/runtime launches a configured VMM/guest image; guest kata-agent supervises container processes through RPC. One sandbox/VM may hold multiple containers. Guest container isolation and VM isolation are different layers; VMM/shim/agent/socket/configuration are trusted infrastructure, not Nexus authorization. Normal Wait/Destroy paths rely on these components; a guest agent result cannot alone prove Host VMM/descendant cessation after a fault. Controller/shim/agent loss needs separately bound Host process inventory/fallback.

KA06 describes veth/TAP/TC and plugin integration; these provide connectivity, not exact destination denial. KA07 exposes virtio-fs/host daemon or block sharing; storage capacity needs a separate quota/capacity mechanism. KA08 documents `sandbox_cgroup_only` alternatives: the described default false mode leaves non-vCPU overhead unconstrained unless infrastructure provisions limits. That dated design must be checked against chosen release/runtime configuration; it cannot be counted as whole-unit resource PASS. Bound VM RAM/vCPUs, guest tasks, Host shim/VMM/IO/virtiofsd overhead, logs and all storage under one envelope.

REUSE a supported VM/container stack if future need justifies its layers; ADAPT Host-and-guest scope/config/identity observations and independent lifecycle controls. Do not rebuild guest agent or infer all descendants are physical Host PIDs. Persistent images/state/shares, tracing/shutdown variants and privilege requirements remain explicit. Larger operational/dependency and evidence graph than a single fixed unit, without ranking it against other families.

## 4. gVisor: application-kernel boundary with Host limits

GV03/GV04: Sentry mediates the guest-facing system API; Gofer and configured directfs/Host FDs provide filesystem access. Host kernel remains TCB; higher-level pre-runtime compromise and hardware side channels remain outside this protection. Current platform guide GV06 describes Systrap and KVM modes with different dependencies. It is a plausible primary isolation layer or defense-in-depth, configuration-dependent; not rejected globally and not a selected mode.

GV05: guest tasks/PIDs are virtualized, so Host pids.max alone does not cap all guest task identities. CPU/RAM aggregation depends on actual Host cgroups covering Sentry/Gofer/helpers plus guest policy; virtual task limits need their own supported scope. GV07 distinguishes sandbox networking from Host mode; disabling networking must close inherited/service/Gofer channels too. GV01 New/Destroy/Signal and metadata expose lifecycle references; attached mode differs from detached use, and some error cleanup is best effort. No source supplies a Nexus hard wall/failure envelope, fixed Host price, grant issuer or protected final receipt. Manager loss/Host faults need separate infrastructure coverage; restore cannot revive authority. REUSE runsc/Sentry, ADAPT exact mode, closed mounts/control/limits and protected observations; REJECT Host-network/directfs broad exposure without explicit accepted scope, automatic weaker-runtime fallback and guest virtual PID reports as Host-wide cessation.

## 5. nsjail: mature process plumbing, monitor is not ultimate fence

NJ01/NJ05: configurable namespaces, mounts/chroot, UID/GID, seccomp/Kafel, rlimits/cgroups and network handling. Parent/configuration/privileged setup remain trusted; workload cannot choose config/mode/capabilities/mount/network helpers. Rlimits are scoped differently from aggregate whole-unit cgroups; file-size/IO limits do not prove total retained disk bound. Input/FD/env/workdir and every child/side helper need closed scope.

NJ02 `reapProc`: tracked child deadlines are evaluated using `time(NULL)` in the monitor loop; expiry sends SIGCONT/SIGKILL. Monitor availability and clock adjustment are therefore dependencies, not a hard controller-independent lifetime contract. NJ03 contains PR_SET_PDEATHSIG setup, parent-race checks and restoration after effective-identity changes; useful defense against a lost parent, not an ultimate physical-fault bound. NJ04 cgroup setup/cleanup must bind supported controllers and real subtree state; cleanup is not assumed from child exit. Root/userns/delegated-resource feasibility is exact-mode dependent and remains untested. REUSE supported nsjail confinement/setup rather than write equivalent Linux plumbing; ADAPT frozen config/input, external cgroups/manager/deadline and evidence; REJECT standalone --time_limit/PDEATHSIG as full P5/P7, networking/listen modes outside admitted fixture and metadata-path recreation after UNKNOWN.

## 6. cgroups v2 and systemd: resources, ownership and timer traps

CG01: cpu.max is scheduler bandwidth, not total runtime; memory.max includes documented transient overrun and separate swap; pids.max counts tasks, not all VM/gVisor guest identities. IO throttling is not disk capacity. Children inherit cgroup membership, but migration/delegation permissions matter. cgroup.kill covers its subtree and concurrent fork; populated readback distinguishes live membership. Removal/path absence is not retained-effect or bill settlement proof. QT01 capacity/inodes need a chosen filesystem/quota or finite backing store.

SD06/SD07: services can receive manager-owned CPU/RAM/tasks and control-group stop/escalation. RuntimeMaxSec default is unbounded, covers active time rather than every start/stop phase and does not bound oneshot activation. Notify/notify-reload EXTEND_TIMEOUT_USEC can extend relevant startup/runtime/stop timers; watchdog pings measure responsiveness and may trigger Restart, not cap useful work. RuntimeRandomizedExtraSec, Exec hooks, Restart, OnFailure/dependencies and manual property/start APIs can add or renew effects. Reject workload access to notify/DBus/cgroup delegation and unauthorized renewal; bind every phase, actual effective properties and a conserved external deadline.

SD01: scopes manage externally created processes and have no main process; attachment can leave a pre-containment execution window. SD03 StartTransientUnit is a mature interface, not permission to expose a generic privileged command API. SD02 resource settings rely on actual controller delegation; user manager rootless limits may be unavailable. Manager reexec/reboot/dependency behavior needs separate failure evidence; OnFailure is an action, not automatic bounded cleanup. Stop requests/exit codes and cgroup-zero-live are separate. Host Agent, watchdog and PID1 can share one kernel/OS/Host failure; WD01 reset/device behavior is not a universal poweroff guarantee. REUSE cgroup/service primitives, ADAPT typed fixed admission/recovery/evidence and an independently qualified fallback; no unit file, service or policy is created.

## 7. OCI/runc/containerd: split creation, broad control and survivor management

OC01 defines stable Host-local IDs, create-before-user-program and separate start/kill/delete/query. Hooks can execute privileged work before the admitted workload and must be trusted/closed or excluded; the create/start barrier is not proof actual reviewed executable bytes were loaded. OC02 configuration carries namespaces/capabilities/cgroups/seccomp, not billing/authority. RC03 shows init setup and exec ordering; supplied bundle/hooks/device/rootfs and resource controls must be reviewed before creation and independently observed before start.

RC02 Signal distinguishes private PID namespace from shared PID scope. In the shared-PID rootless-cgroup failure path it warns and signals init, acknowledging possible leaks without delegation. Also Set can fail rolling back resource settings and warn state/config inconsistency. A wrapper must treat relevant downgrade/drift as STOP, verify exact process start identity/subtree and never make kill-request = cleanup. runc is a runtime command/library, not an independent whole-lifetime manager; command parent death need not stop detached workload. RC01 rootless is possible with kernel support, not proof delegated resources exist.

CD01/CD02 add daemon, shim API, state/events, subreaping and cleanup/reconnect machinery; daemon and shim are distinct, so daemon loss is not a guaranteed stop. Shim scope can group containers; runtime paths/options/plugins and snapshots add privileged surface and persistent state. Subreaper collects exited processes; it does not kill live descendants merely by existing. Image/content, container metadata, task, exec process, snapshot and log deletion are distinct. REUSE a supported runtime/shim if its surface is justified; ADAPT fixed runtime paths/profile/custody/original references/independent limits and cleanup. Do not yet choose direct runc, containerd or higher-level stack. REJECT broad socket access, arbitrary hooks/runtime selection and daemon state as protected Nexus evidence by default.

## 8. bubblewrap: construction primitive, not a policy or complete lifecycle

BW01 explicitly places sandbox security policy with the caller's argument builder. Current README says historical setuid mode was removed; stale comparison prose is not a current privilege contract. BW02 constructs namespaces/mounts, no_new_privs, optional seccomp/FD/status and parent-death behavior; --die-with-parent invokes PDEATHSIG, useful but not an independent ultimate deadline. Network namespace choice, passed descriptors, mounted sockets, terminal/TTY and capabilities determine reachability. D-Bus mounts can expose external command paths; parent protection and no inherited owner service socket are essential. PID1/reaper behavior does not itself prove all externally visible resources released.

REUSE minimal construction only with future exact release/system support and externally applied resource/lifecycle controls. ADAPT a fixed reviewed argument/policy builder and actual-effective observations, without a generic command surface. REJECT bare successful bwrap launch as qualification, caller/workload-selected policy, broad Host mounts and sole parent-death lifecycle. Persistence/billing, protected evidence and effect reconciliation remain outside. No rootless kernel/userns availability is assumed for this Windows environment.
