# Nexus G2 Route B OpenAI-Hosted Agents API Support Question Pack v1

Status: **PROPOSED CLARIFICATION PACK — NOT SUBMITTED; NO OUTREACH AUTHORITY**

Evaluation target: OpenAI Agents API, OpenAI-managed Codex harness, `environment.type: "openai_hosted"`, one Linux sandbox per session, beta header `OpenAI-Beta: agents=v1`.

This pack asks only for official contract, API-reference or service-documentation semantics required by the accepted Nexus provider-neutral Host contract. Each question asks one semantic. “Guaranteed” means an enforceable provider behavior for this exact hosted mode, not a default, recommendation, dashboard observation or best-effort behavior. No Nexus secret or internal implementation is disclosed.

1. **P1 — deployed identity:** Which supported response field or provider record identifies the exact hosted sandbox image/runtime and enforcement implementation revision actually used by one `environment.id`, rather than only the requested environment type and size?
2. **P1 — loaded workload identity:** Is there a supported provider-side record binding the executable/script and dependency bytes actually loaded for a command/tool item to its environment, session and turn IDs; if so, what is the field, retention and integrity contract?
3. **P1/P8 — command identity:** Does every hosted shell command have a stable operation ID and retrievable terminal result that a fresh client can query after stream disconnect, process exit, sandbox expiry or session cancellation; what are the lookup and retention semantics?
4. **P2 — actor graph:** Which actor classes and credential scopes can create, inspect, add files to, steer, update, cancel or delete an OpenAI-hosted session/environment, including project members, service accounts, managed harness components and support/operations actors?
5. **P2/P3 — mutation exclusion:** After session creation, which environment properties can any actor mutate (network, files, packages, setup, template-derived configuration, capabilities or credentials), and is there a provider-guaranteed interval in which the admitted configuration cannot change before/during execution?
6. **P3 — applied policy receipt:** Which supported provider-side readback proves the effective network policy and all relevant sandbox restrictions applied to one `environment.id`, with observation scope, timestamp/freshness and enforcement revision?
7. **P3/P4 — disabled-network scope:** Does `network.access: "disabled"` hard-block all guest-originated IPv4/IPv6, DNS, redirects, link-local, metadata, private/internal service and alternate-protocol egress for every descendant, apart from explicitly documented provider-internal channels; what exceptions exist?
8. **P4 — complete channel graph:** For a session with no tools, MCP, vaults, skills, plugins, capability directories, setup commands or packages, what provider/harness, filesystem, IPC, local-service, environment-file mutation and indirect execution channels remain reachable by sandbox commands?
9. **P5 — hard compute limits:** Are selected vCPU and memory values hard whole-sandbox enforcement limits for all descendants, and what exact behavior occurs on CPU contention or memory exhaustion?
10. **P5 — complete resource limits:** What hard nonrelaxable storage, PID/process-tree, file-descriptor, output/log, artifact, background-process and other resource limits apply to the complete hosted sandbox, and which response/readback binds them to one environment?
11. **P5 — active lifetime:** What provider-enforced maximum wall-clock lifetime applies to an active turn, session and hosted sandbox, including continuous activity, keep-alives, background descendants and loss of the application client?
12. **P5/P7 — cleanup completion:** After active-turn cancellation and session deletion, what bounded terminal signal proves all sandbox descendants and background work have stopped and physical cleanup has completed, rather than only public API removal?
13. **P6 — model-loop bound:** Which creation setting imposes an enforceable finite maximum on total root/subagent model calls, retries, reasoning/output tokens and tool-loop steps for one session or turn, including provider retries?
14. **P6 — complete charge composition:** What are all billable dimensions for the exact hosted mode with disabled network and no optional tools/vault/MCP, including model, container, files/artifacts/storage, idle/cleanup time and delayed/residual charges?
15. **P6 — hard financial ceiling:** Which provider control can enforce a finite per-session/turn maximum charge before dispatch, and what are its maximum lag, overshoot and treatment of in-flight work?
16. **P8 — retention/not-found:** What guaranteed retention and expiry apply to sessions, turns, saved items, command results, artifacts, traces and webhook records, and how does each API distinguish never existed, deleted, expired and temporarily unavailable?
17. **P8 — observation completeness:** Which command output, exit/failure, truncation, background work and unpublished-output facts are guaranteed to appear in saved items or another retrievable provider record when a turn completes, fails or is cancelled?
18. **P9 — idempotency/reconciliation:** What idempotency key and lookup contract applies to session creation and input submission after a lost response, so a controller can resolve whether the original operation occurred without creating or submitting a replacement?
19. **P9 — post-delete effects:** Which durable record remains after environment expiry or session deletion to reconcile original command execution, artifacts, external effects and asynchronous physical cleanup?
20. **P10 — complete provider receipt:** Is there an integrity-protected provider record binding actor/project, session/environment/turn/command IDs, actual deployed revision, applied configuration, admitted input identities, timestamps, terminal result, artifacts and cleanup state; what is its retention and authenticity contract?
21. **P10 — event/trace completeness:** What completeness, ordering, replay and retention guarantees apply to saved items, signed webhooks and trace export, including records that arrive after turn completion or after a 72-hour webhook retry window?
22. **P11 — revocation propagation:** When an application API key or relevant project/service-account authority is revoked or rotated, what bounded effect occurs for existing sessions, active turns, event streams, environment file access, vault grants and concurrent authenticated clients?
23. **P12 — material drift:** Which supported deployed image/runtime/harness/network-enforcement identity and material-change notification lets a client detect that a previously qualified hosted configuration must be requalified?
24. **P12 — beta contract:** What compatibility, deprecation and change-notification guarantees apply to `OpenAI-Beta: agents=v1`, especially for security-, lifecycle-, observation- and billing-relevant semantics?

An answer is useful only when it cites a current official public/contractual source or identifies a supported response/API field and states whether the behavior is hard or best effort. Answers limited to configuration intent, current implementation, account dashboard state or one observed run remain insufficient.
