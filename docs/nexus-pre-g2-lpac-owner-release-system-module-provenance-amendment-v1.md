# Nexus Pre-G2 LPAC Owner Release: System-Module Provenance Amendment v1

Status: **PROPOSED BOUNDED AMENDMENT FOR DOCUMENT REVIEW AND OWNER ACCEPTANCE**

Date: 27 September 2026

## 1. Decision and exact supersession

The accepted *Owner Release Boundary Amendment v1*, under **Same-process loaded-code binding**, and its *Verifier Implementation Spec v1* under its process/image and dependency observation rules require comparison of executable mapped sections against reviewed file bytes after reviewed relocation/import normalization. As applied unconditionally to Windows system modules, this makes raw mapped-versus-file byte equivalence a gate despite the accepted *G2 Host Qualification Scope & Exit Decision v1* treating the Windows kernel, loader and configured Code Integrity as a bounded TCB. The accepted *G2 Host Qualification Evidence Successor Protocol v1* §2.2 supplies the replacement system-module provenance rule.

**This amendment supersedes only the unconditional mapped-versus-file executable-byte equivalence gate for verified Windows TCB/system modules, whether stated as raw equality or as comparison allowing only the previously reviewed PE relocation/import normalization.** It also narrows the earlier Owner Release STOP phrase “weakened mapped-byte standard” solely to permit this expressly accepted system-module exception. It does not remove the requirement to bind the actual module loaded into the same process to a reviewed, protected physical image; it does not change the rule for Nexus-controlled code, including controller, watchdog, verifier-observed recovery, LPAC probe/canary and their Nexus-controlled executable dependencies. Historical accepted documents retain their exact bytes and remain authoritative on every unaffected point. The successor protocol's handle/PSS rule is governed by that protocol's separate acceptance, not by this mapped-byte amendment.

## 2. Two code classes and bounded proof

**Nexus-controlled code.** The accepted strong actual-loaded identity/provenance requirement remains intact: protected reviewed file object and byte basis held across check/create/load; same-process creation/load event, physical volume/file identity and mapping base; mapped executable section comparison against reviewed PE bytes with only explicitly reviewed relocation/import normalization; demonstrated pre-instruction or pre-effect ordering; monitored relevant late executable loads. A prelaunch hash, path, manifest membership, signature or child assertion alone cannot PASS. A null/unresolvable load-event handle, substitution, byte mismatch, unstable object or unsafe ordering remains STOP/FAIL as applicable. This amendment offers no relaxed comparison for Nexus-controlled components merely because a Windows DLL is also present.

**Windows TCB/system modules.** Apply *Evidence Successor Protocol v1* §2.2, not unconditional raw mapped==raw disk bytes. Independently bind a valid same-process module load event and mapping base to a stable physical volume/file identity; establish protected canonical Windows component location, exact OS build and approved file/version/hash inventory, applicable Microsoft/Windows signature or catalog trust, configured CI policy and relevant enforcement result. A valid actual-load binding is mandatory: path, signature, CI record or on-disk hash alone does not establish that the process loaded that image. A null event file handle has **no automatic fallback**; STOP until a separately reviewed, supported OS-backed method binds the same mapping to physical file identity and trust. Reject writable, substituted, unexpected-location, untrusted or unresolved images. Preserve actual-load ordering and dependency closure. The unexplained historical `ntdll`/`kernel32`/`KernelBase` mapped-byte differences are not declared benign or experimentally qualified by this decision.

**Accepted Windows TCB.** Nexus trusts Windows kernel process/token/object/ACL/Job enforcement, the Windows image loader's mapping of the verified system image and the configured Code Integrity enforcement at their stated scope. Nexus proves the observable Nexus-to-Windows boundary above, rather than independently re-proving arbitrary internal loader transformations. This trust does not extend to an attacker-selected DLL, writable system lookalike, compromised owner/SYSTEM/kernel or a bypassed/unknown CI state. Any new concrete threat outside this boundary requires a separate architecture review.

## 3. Fail-closed effect and exclusions

For every required system module, a mismatch or positively observed substitution is **FAIL**. Missing, stale, contradictory or nonindependent actual-load identity, trust basis, path protection, build/hash anchor, ordering or dependency closure is **UNKNOWN/STOP**. An unknown does not become PASS because it resembles a known Windows module. Current staged verifier and current local protocol remain STOP at their existing gates until a governed accepted protocol/package successor and exact implementation bytes implement this rule and are separately authorized. The accepted no-outer-Job, fixed four scenarios, owner-only evidence, protected package path, watchdog/Job/failure semantics and all HQ1–HQ5 properties remain unchanged.

This amendment adds no generic loader verifier, arbitrary loader reverse engineering, general Application Control administration, broad allow rule, signing infrastructure, recursive verifier, generic launch surface, privileged broker/service, network capability or provider authority. It does not change Pre-G2 A0–A6, Option D, Option A HOLD, E2B qualification, HQ6 or G2. Acceptance is documentary architecture/protocol governance only: it does not mark a Host property PASS, approve a qualification package, authorize LPAC Scenario 01–04 or release G2 HOLD. Positive Host Binding remains ABSENT.
