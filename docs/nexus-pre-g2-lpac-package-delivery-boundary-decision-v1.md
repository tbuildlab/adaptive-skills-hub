# Nexus Pre-G2 LPAC Package Delivery Boundary Decision v1

Decision ID: `nexus.pre-g2.lpac-package-delivery-boundary.v1`
Version: `1.0.0`
Date: 27 September 2026
Status: **PROPOSED — NOT ACCEPTED — NO IMPLEMENTATION OR EXECUTION AUTHORITY**

## 1. Decision and scope

The accepted LPAC architecture remains the isolation contract. The local qualification was stopped before Scenario 01 because the Codex Desktop command path was in an outer Job. A subsequent read-only delivery audit found a second, independent STOP: the fixed package under `D:\chatgpt\安装skills\output\nexus-g2-feasibility-2026-09-16\LPAC-TRUSTED-OBSERVER-DESIGN-2026-09-24` inherits non-owner Modify/Delete permissions. `D:\chatgpt\安装skills\output` is owned by `CodexSandboxOffline`; the non-elevated De Yong token does not own it. The 43-entry package remains byte-valid (manifest SHA-256 `B3FD83240F4D1FA65B3C005E1C358BF4EA2EB7B372445F09E3222BD926894ECC`), but hashes in that mutable location do not establish an owner-controlled launch path. No qualification profile, child or receipt was created.

This proposal corrects **only package delivery and owner evidence custody**. It does not change the accepted LPAC token, empty capability set, six-name child environment, zero-child-handle rule, Job/watchdog ordering, four fixed scenarios, denial tests, default-deny decisions, or cleanup criteria. It does not grant authority to run any scenario. The historical D: package is retained as preparation evidence and is never an authorized source of runtime bytes after a successor package is accepted.

The trust chain is: mutable development/build workspace → reviewed candidate bytes → owner-controlled staging → sealed, versioned qualification package → independent pre-execution verification → non-elevated owner-launched controller and watchdog outside any outer Job → fixed LPAC child → separate owner-only evidence → exact cleanup. A hash, path, receipt, or owner shell assertion alone cannot skip a link.

An Administrator/SYSTEM compromise is outside this local owner boundary and cannot be described as prevented by a user DACL. No administrator token or privilege is part of the qualification runtime.

After staging, package contents must have a protected DACL denying non-owner mutation and allowing the owner only the access needed to read/execute and verify. The owner can always change ACLs on owner-controlled objects; therefore “sealed” means independently hash-bound, ACL-protected against *other* principals, and rechecked at release, not cryptographically immutable against the trusted owner. Evidence remains owner-writable at fixed names; `CREATE_NEW` must fail on any existing receipt. A child-authored status file is corroboration only.

Parent-path protection is conjunctive: neither `DELETE` on a path component nor `DELETE_CHILD` on its parent may let an unrelated principal rename, remove or substitute the next component. Check the exact effective ACE mask rather than the label “read-only”; reject inherited write/delete rights and any parent reparse/rename opportunity. If the chosen implementation cannot demonstrate this for every mutable ancestor and reviewed artifact, STOP before profile creation. ## 4. Promotion from development to the trusted package

The D: development/output tree is an **untrusted source of candidate bytes**. Its existing manifest is historical correlation, not an execution grant or sufficient evidence that staged bytes are reviewed. A separately authorized implementation must:

1. Freeze an explicit source/build inventory, toolchain, four cases, exact roots and allowlisted files. Reject extra binaries, scripts, writable plugins, unsigned dynamic search paths and unreviewed dependencies. Do not execute source-tree binaries to qualify the new boundary.
2. Make a new versioned source/protocol package that splits the old `NEXUS_EVIDENCE_ROOT` into fixed `PACKAGE_ROOT` and `EVIDENCE_ROOT`. Rebind the controller's self/watchdog/module/PDB paths and watchdog working directory, watchdog receipt path, all recovery receipt paths, and the offline PDB utility's input path. Replace the probe's old D: negative-access target (`LPAC-ARCHITECTURE-ACCEPTANCE-2026-09-24\baseline.tar`) with a fixed synthetic canary under the new owner-only evidence root; the LPAC must receive no access to the new package or evidence. Regenerate the module/TCB inventories whose source-path columns name the old root. Search every source, generated input and executable dependency for stale old-root literals. Keep the D: synthetic work paths only where deliberately accepted.
3. Rebuild every binary whose embedded bytes change. Review exact source diff, build flags, x64 PE identity, static diagnostics, fixed scenario selection and dependency closure. A binary may be reused only if its bytes, embedded paths and role are demonstrably unchanged and it is explicitly listed in the successor manifest. The existing 43-entry manifest cannot be relabeled as the new runtime manifest.
4. Create the protected owner root and empty subdirectories with fresh exact names; record pre-creation absence, parent IDs/ACLs and resulting owner/DACL. Copy only the new allowlist into `package` using no-overwrite creation, with reparse/alternate-stream rejection. Preserve a source→destination mapping and SHA-256 for each copied object. Never execute directly from the mutable source.
5. Independently re-open and hash **staged destination bytes**, lengths and file IDs. Build a new versioned manifest rooted at the exact C: package path, binding every reviewed source, all four controllers/watchdogs/probes/canaries, recovery, module/API inventories, PDB GUID+age/hash, toolchain, expected OS/ntdll version/hash and the fixed evidence/work path identities. Validate the manifest from the protected destination and record its independently reviewed digest outside the untrusted development tree. Any mismatch or stale old path is STOP. The owner must review and explicitly authorize these **new exact bytes** before they become the only qualification-authorized artifacts.
6. Seal package ACLs, read back effective ACLs and hashes, and repeat identity/path/hash/OS checks immediately before each attempt. The trusted controller must hold the reviewed image/dependency objects stable through load and bind actual same-process debug-event file IDs, mapped image bases and bytes as already required. A path plus a pre-launch hash does not qualify loaded code. No new arbitrary command, provider or runtime selection is introduced.

The preparation package remains untouched at its old D: path, marked **historical / not for qualification execution** in the successor record. New binary/manifest names must be versioned; no silent overwrite of the old 43-entry package or its original STOP result. If the current Windows image or PDB changes, regenerate and review a new exact pair rather than accepting stale offsets. Microsoft `CreateProcessW` permits exact application, environment and current-directory parameters; the accepted controller/child checks remain mandatory [Microsoft CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw).

## 5. Pre-execution launch, evidence and TOCTOU gate

The owner opens a fresh ordinary, non-elevated Windows shell **outside** Codex Desktop and launches only the exact reviewed C: controller binary after the successor package is accepted and separately authorized. UI origin is not evidence of Job status. The controller must reject the wrong owner SID, elevation, AppContainer token or *any* outer Job before creating the profile; its fixed watchdog independently repeats the owner/elevation/no-outer-Job checks and must produce its flushed ready receipt before Job or child creation. No `CREATE_BREAKAWAY_FROM_JOB`, Task Scheduler, privileged broker or alternate account is permitted.

Owner-side preflight must independently verify the staged package digest and each file, all ancestor and object ACLs/IDs, no reparse point, exact unused receipt and attempt names, OS/PDB anchors, executable image/dependency identity and no unexpected process. The controller's own self-binary-hash report corroborates but does not replace independent verification of the reviewed binary and its loaded image basis. If an owner-launched direct process cannot maintain check-to-create path/file stability or cannot bind the actually loaded controller bytes to the approved artifact, STOP and review a narrower fixed-purpose verification mechanism before any qualification profile; do not treat a shell transcript or self-report as proof.

The controller still constructs the LPAC child's six-name fresh environment, fixed work/TEMP values and zero inherited handle policy, then verifies the same process through the accepted token, PEB/PSS, image/dependency and Job observations. The shell's environment or inherited standard handles never become the child's policy. The watchdog receives only its reviewed ready handle and fresh minimal environment. Effective runtime facts remain UNKNOWN until observed; this delivery decision cannot declare LPAC PASS.

All controller/watchdog/recovery receipts use fixed, previously absent paths under `evidence`, explicit owner-only security descriptors and `CREATE_NEW`; flush and bind the record to package digest, attempt ID, returned process PID+creation time, observed source/scope and cleanup. The evidence directory itself must resist non-owner write/delete, parent rename and substitution. Reject a duplicate, missing, truncated, inconsistent or writable-by-unrelated-principal receipt. After each attempt, a separate read-only reviewer compares actual evidence and current file IDs/hashes/ACLs with the approved manifest. If a reviewer cannot read the owner-only originals, the owner may export a secret-free, hash-bound review copy after cleanup; that copy is a transport artifact, not the authoritative receipt, and no sandbox principal gains write access to the originals. An exit code, status-only child file or package hash alone is not acceptance. Windows `CREATE_NEW` fails if the target already exists [Microsoft CreateFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew).

## 6. Threats and falsifiable gates

| Threat | Required prevention/observation; otherwise STOP |
| --- | --- |
| Malicious or accidental development-tree change | Never launch there; review exact new source/build bytes; compare staged destination to approved manifest. Source digest alone is insufficient. |
| Modification during staging | Fresh no-overwrite destination, owner-only DACL, independently rehashed destination and source→destination mapping. No reparse or alternate stream. |
| Post-verification replacement or stale binary | Protected whole path, held IDs/file objects through load, recheck before each attempt, loaded-image/dependency byte binding. No old-root literal in runtime bytes. |
| Parent rename, `DELETE` or `DELETE_CHILD` | Inspect every ancestor and next component; no unrelated principal may rename/delete/substitute any link. Any effective parent/target permission uncertainty is STOP. |
| Inherited writable ACE or sandbox identity | Protected DACL on new root and both child roots; read back each staged file. No sandbox or broad group write/delete/read of owner-only material. |
| Reparse point, mount/junction or path alias | Resolve and record exact canonical paths, reparse tags, volume/file IDs; reject unexpected reparse at every component, before and after staging/launch. |
| Evidence replacement or forged receipt | Owner-only evidence tree and `CREATE_NEW`; bind fixed attempt and process identity; compare controller/watchdog/recovery records and OS-side readbacks. |
| Privileged OS actor | SYSTEM/Administrators are an explicit OS-level residual TCB, not a claimed adversary excluded by ordinary user DACLs. No new privileged broker or runtime dependency is allowed. |
| Staging/launch TOCTOU | Owner-controlled path and stable held objects; independent destination hashes and same-process actual load observations. Missing independent proof is STOP, never inferred from successful compilation. |

## 7. Cleanup, rollback and authority

Runtime cancellation, Job/watchdog deadlines, controller-loss recovery and zero-active-process verification are unchanged. Only after those settle may the exact attempt's synthetic D: tree and AppContainer profile be removed. The owner-only evidence stays available for review; a failed/unknown cleanup preserves the new package and receipts, blocks later cases and forbids retry under the same IDs. No broad recursive cleanup, deletion of historical evidence or fallback to the D: preparation binaries is authorized.

Before any future staging, capture exact parent/root SDDL, owners, volume/file IDs, source/target hashes, absence of proposed paths and a rollback plan. On setup or staging failure **before any child**, close held handles and remove only objects newly created by that attempt when their identities and absence of live users are proven; preserve a status-only failure record. If any object or ACL cannot be restored deterministically, STOP and leave it for owner investigation. After acceptance, a flawed version is abandoned with preserved evidence and replaced by a separately reviewed version; it is never silently rewritten in place. The shared D: development/output ACLs and historical package are not changed.

This proposal is additive to the accepted AppContainer architecture; it would supersede only that architecture's local package/evidence path assumptions, not A0–A6 or LPAC isolation semantics. The accepted AppContainer architecture and acceptance record remain historical and unchanged. Implementation would require a successor to external `04-observer-implementation-design-v2.md`, `05-local-qualification-protocol-v2.md`, `06-adversarial-review-round2.md` and `07-pre-execution-package-manifest-v1.json`, plus rebuilt/reviewed affected binaries and a new owner acceptance record. The E2B protocol successor, provider cost boundary and G2 Host qualification remain separate. This proposal does **not** inherit the previous four-scenario authorization for new bytes/paths. Architecture acceptance, package implementation, owner authorization of the new exact package, local LPAC qualification, network-capable LPAC qualification, E2B G0, positive complete Host binding and G2 acceptance are separate gates.

Current state remains Option D: no positive Host binding and G2 HOLD. No root, ACL, profile, Job, process, credential or provider resource is created by this document. Acceptance of this proposal would authorize **no implementation or execution** without a separate owner instruction.
