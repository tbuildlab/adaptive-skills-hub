## 2. Method, expected controls and evidence limits

This is a manual static application of accepted semantics, not code that selects gates. First declare each fictional subject, task scope, criterion and input provenance; then select relevant subchecks, required evidence and unresolved outcomes. Expected guards are derived from accepted source sections: no universal gate execution, no mandatory-UNKNOWN downgrade, no keyword-only D01, and separate diagnostic/repair facts. The adversarial pass changes profile facts in ten paired variants; it does not invent new rules to force the expected answers.

**Every scenario fact, trace and result below is SYNTHETIC / STIPULATED.** No fictional input/output file, public endpoint, UI, detector, fix or regression executable was created or run. Within-case conditional conclusions describe what would follow if its stipulated evidence were independently available and bound. A synthetic validation PASS never establishes a real application check PASS, actual capability EXECUTED/APPLIED or provider effect. Actual verified facts in this checkpoint are repository bytes/state, documentary consistency and the separately reported existing repository tests.

Applicability and evidence satisfaction are separate: REQUIRED selects an obligation; missing actual proof remains UNKNOWN. OPTIONAL is not performed merely by being listed. NOT_APPLICABLE needs a positive profile reason. DEFERRED identifies relevant future work/prerequisite without permission or satisfaction; an existing required deferred property still blocks the related claim. Security-relevant ambiguous profile facts stay UNKNOWN and prevent affected action. No unseen fact is inferred absent from the word local, demo, read-only or synthetic.

Gate names are the accepted families: A capability/pre-build; B design/content/truthfulness; C accessibility; D security/privacy/provider effects; E SEO/release/handoff; F scoped acceptance. D01 labels TRIGGER/NOT_TRIGGER below are only this exercise's answers, not new runtime enums. TRIGGER_LIGHTLY is not needed for the base cases; relevant ordinary path checks can apply while no new D01 boundary is introduced.
