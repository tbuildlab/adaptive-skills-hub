# Nexus LPAC Owner Release Boundary: Architecture Amendment Proposal v1

Status: **PROPOSED ONLY — NOT ACCEPTED — NO IMPLEMENTATION OR EXECUTION AUTHORITY**
Date: 27 September 2026
Classification: **B — bounded amendment requiring separate owner acceptance**

## Decision and scope

Package Delivery Boundary Decision v1 §5 requires independent binding of the owner-launched controller's actually mapped image to reviewed destination bytes. Its current launch rule names a direct owner launch of the controller. The reviewed C: package has no independent mechanism that can satisfy this gate; a shell command, prelaunch digest, path, exit code or controller self-report cannot do so. Decision v1 §5 explicitly calls for review of a narrower fixed-purpose mechanism when direct launch cannot prove the binding. Its adversarial review requires a separate versioned decision if a new trusted component is necessary. This proposal is that **bounded successor decision**, not a claim that the existing rule already authorizes code or execution.

The proposed same-owner, non-elevated **release verifier** would add one trusted qualification component between the owner's single command and the four fixed controllers. This changes the accepted direct-launch wording and adds a small trusted computing-base member, so classification A is false. It creates no new account, privilege, service, broker, provider or general execution interface. Its authority is limited to the four enumerated qualification cases, which makes a bounded amendment plausible rather than a new general Host architecture. If the required OS evidence needs elevation, a privileged broker, an arbitrary path/command interface, or a weaker proof, classify the result as C and abandon this proposal.

The existing 40-member package, manifest SHA-256 `216A9AD9EE8F4D1C1A3A6CC70ED7094607DD957AEB57DD02C538FBE6B9C49B98`, and owner evidence remain historical static candidates. **Do not edit or execute that sealed package.** The proposed successor root is exactly `C:\Users\De Yong\NexusQualification\LPAC-Local-Delivery-v2`, with protected `package`, `evidence` and controller-private temporary children; its existence, owner, ACL and ancestor stability must be established afresh. Acceptance would permit a separately authorized, versioned rebuild and static implementation experiment; it would not authorize creation of that root, an LPAC profile, Scenario 01–04, E2B, network capability, credentials, or G2.

## Fixed trust boundary

The owner starts one exact reviewed verifier binary from a fresh ordinary non-elevated De Yong shell outside Codex Desktop. The shell supplies no trusted claim. The verifier accepts no executable path, command, case selection, URL, policy, capability, secret or provider argument. A fixed internal sequence selects the four named controller images and the case-03 recovery image in the accepted order, stopping after any incomplete case. The same pre-instruction mapped-byte and loaded-dependency gate applies to the verifier-launched recovery process. The controller/watchdog retain all existing token, no-outer-Job, Job, debugger, deadline, receipt and cleanup duties. The verifier cannot replace or waive their independent checks. It also cannot treat a manifest hash as independent mapped-byte evidence for the controller-created watchdog; the accepted watchdog byte/load observations must be cross-checked, and any remaining mapped-byte requirement that they do not satisfy is STOP pending a reviewed correction.

The verifier must establish its own exact De Yong SID, interactive non-elevated token, absence of AppContainer identity and absence of an outer Job before opening a candidate controller for execution. It must verify the exact reviewed package/manifest digest, current OS/PDB anchors, protected parent chain, owners/DACLs, reparse state and volume/file IDs. It must reject any broad write, DELETE, DELETE_CHILD, rename, reparse, alternate stream, unexpected hardlink, unexpected object, changed manifest or existing receipt. It holds relevant file and directory objects against write/delete/rename across the load window. Its source, binary, imports, loaded dependencies and protected package custody are themselves reviewed and pinned; the owner shell is not an attestation root. The remaining verifier bootstrap trust in the owner-controlled package and Windows process loader is explicit and must be accepted, not hidden by a self-hash.

## Same-process loaded-code binding

For each fixed controller, the verifier constructs a fresh allowlisted Unicode environment and fixed working directory. It creates the exact binary with `CreateProcessW`, explicit `lpApplicationName`, `bInheritHandles=FALSE`, `CREATE_SUSPENDED`, `CREATE_UNICODE_ENVIRONMENT` and `DEBUG_ONLY_THIS_PROCESS`. `CREATE_BREAKAWAY_FROM_JOB` is forbidden. It retains the returned process and primary-thread handles and records PID **plus creation time**, process-handle identity, token and no-outer-Job readback. The debug flag must not attach to LPAC descendants; the controller's own `DEBUG_PROCESS` observation must remain independently effective. This interaction is an experimental UNKNOWN until demonstrated.

Before any controller application instruction is permitted, an independent OS-side observation must bind the returned process's `MEM_IMAGE` main mapping and mapped byte basis to the held reviewed controller file object, not just a path. The `CREATE_PROCESS_DEBUG_EVENT` image `hFile` and `lpBaseOfImage`, when valid, are candidate corroborating OS facts. The verifier must compare stable volume/file ID, length and independently hashed file bytes with the approved artifact, and compare mapped image sections with the expected PE image after explicitly reviewed loader relocations/import fixups. It must prove the debug event belongs to the same returned process/creation time. A null/unreadable event handle, inaccessible mapping, unexplained byte difference, or inability to establish the required pre-instruction ordering is STOP. `CREATE_SUSPENDED` alone does not prove loaded bytes.

Every dependency that can affect the trusted controller boundary must have a closed approved identity and byte basis. `LOAD_DLL_DEBUG_EVENT` `hFile` and base, when valid, are candidate OS observations. The verifier must continue monitoring the same process for late loads. No unexpected or unbound DLL may execute code or affect a qualification operation. The exact ordering between a DLL-load notification and its executable initialization must be demonstrated, not inferred from API names; if it cannot be demonstrated, STOP. A null event `hFile`, API-set/KnownDLL alias or system module must have an independently reviewed OS-backed resolution to an exact physical image/byte basis, or STOP. System DLL/PDB drift requires a new reviewed package. File hash and mapping observations are not a claim of whole-memory immutability after release; unexplained modification or new executable mapping invalidates qualification.

## Release, failure and custody

The verifier may resume the suspended controller only after the independently observed main-image gate, every dependency already observable while suspended, package path stability and predeclared process facts pass, and after a flushed owner-only `CREATE_NEW` pre-resume receipt. Other dependencies may first appear during loader startup after `ResumeThread`; their load events must be independently bound **before their code can execute or affect a qualification operation**. Resuming for OS loader activity is not a PASS or permission for controller application code to run before its main-image proof. A technical question remains whether a Windows debug event can be received while the primary thread remains suspended and whether subsequent load events gate each DLL before executable initialization. The implementation experiment must demonstrate this ordering on this Host. If it cannot, STOP; do not relabel post-execution evidence as pre-execution proof.

The verifier must keep monitoring later DLL loads until the exact controller ends or the attempt is stopped, without interfering with the controller's LPAC debugger. It never edits the debuggee's memory or context. On any mismatch, timeout or partial record, it terminates the bound controller, waits, reconciles all bound process identities and preserves a status-only failure receipt. A verifier crash must not leave an unobserved controller or LPAC child: debuggee kill-on-debugger-exit is only a candidate safeguard; its actual behavior and the existing watchdog/Job fail-safe must be demonstrated together. The verifier cannot detach or set kill-on-exit false. A cleanup ambiguity blocks every later case. Receipts reside only in the owner-protected evidence root, use fixed unused names, explicit owner-only ACL, `CREATE_NEW`, flush, a monotonic sequence, exact package digest and process identity; child output corroborates only.

## Architecture relationship and decisions reserved

This is an additive, versioned amendment to Package Delivery Boundary Decision v1 §§4–6, specifically replacing its direct owner-to-controller launch wording with one owner-to-verifier-to-controller path. It does not alter Pre-G2 A0–A6, the accepted LPAC token/capability/isolation model, fixed four scenarios, watchdog/deadline semantics, or E2B successor protocol. Accepted records remain historical; a separate acceptance record must name the exact amendment SHA-256 and supersession scope. A future implementation must version the protected package, manifest, protocol/design/adversarial review and exact destination hashes; it must obtain explicit owner approval of those bytes before execution. No previous authorization transfers automatically.

**STOP/abandon:** any need for elevation, cross-account token, password transfer, Task Scheduler, privileged service/broker, breakaway, broad command surface, secret, network/E2B resource, weakened mapped-byte standard, unsafe loader/debugger interaction, unverifiable dependency, unbounded verifier crash, or unrecoverable evidence custody. Such a result requires a separate architecture alternative, not a quiet implementation tweak.
