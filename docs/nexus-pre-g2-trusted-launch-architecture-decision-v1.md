# Nexus Pre-G2 Trusted-Launch Architecture Decision v1

Decision ID: `nexus.pre-g2.trusted-launch-decision.v1`

Decision version: `1.0.0`

Decision date: 24 September 2026

Status: **PROPOSED ADDITIVE ARCHITECTURE HOLD — NOT OWNER-ACCEPTED — NO IMPLEMENTATION AUTHORITY**

## 1. Decision and scope

The current architecture state is **Option D: the required trusted-launch Host primitive is unavailable**. There is no positively qualified G2 Host binding. E2B G0 remains blocked before Sandbox creation at the independently verifiable launch of the restricted Windows executor. Option A, a fixed-purpose owner-controlled Windows launcher, is the smallest conditional candidate; it is not selected for implementation because no acceptable source of a `NexusTest` primary token and no independent launch-attestation path have been established.

This is one additive status decision under the accepted Pre-G2 architecture, not an amendment to its A0–A6 text. It changes no frozen artifact, Host integration, capability profile, grant, or qualification status. It authorizes no launcher implementation, Host-isolation rerun, E2B Sandbox, G2 dispatch, or G2 implementation. A later change to the token/acquisition trust boundary requires a separate versioned architecture amendment, explicit owner re-acceptance, and separate bounded implementation authorization before any code experiment.

## 3. Conditional Option A trust boundary

If a future amendment establishes an acceptable token and observation source, a launcher may be a small fixed-function **Host integration harness**, outside the frozen R2/R4/R5 interfaces. Its only authorized function would be to launch one exact reviewed executable under the exact `NexusTest` identity for one bounded qualification attempt, observe its lifecycle, and terminate its process tree. The trusted owner/controller chooses and pins the executable bytes, attempt identifier, fixed paths, environment specification, allowed standard streams, and time bound before launch. The restricted process receives none of the owner's API key, credential store, browser session, SDK object, environment block, profile rights, or general command surface.

Windows applies the selected token, environment block, and handle-inheritance parameters at process creation; directory ACLs are enforced when protected resources are accessed. Process-tree containment and any Job Object constraints must be established and verified before the child is permitted to execute. The launcher must prove the exact values it supplied and verify the resulting process. A child may later change its own environment, so an environment inventory after launch is corroboration, not a replacement for trusted creation evidence. The launcher is part of the trusted computing base and must be protected from modification or invocation with arbitrary input by `NexusTest`. The restricted process and its return file are subjects of observation, not the authority for their own launch attestation. The owner controller's access to its own credential store makes unintended inheritance, handle duplication, logging, or path substitution a critical risk even if the launcher never intentionally reads a key.

At this stage, the launcher would be only a fixed-purpose qualification facility for the designated, still-unqualified E2B candidate. Only after independent Host qualification succeeds may a later narrow execution adapter be considered. The launcher must not become a generic Agent/Skill runtime, shell, task scheduler, arbitrary executable/argument dispatcher, privileged multi-user broker, credential service, E2B control plane, sandbox replacement, or persistent daemon. Adding any of those roles requires its own architecture review and cannot be inferred from this decision.

## 4. Primary-token source decision — unresolved and blocking

An acceptable source must give the trusted launch controller a real **primary** token for `DESKTOP-MEQBS2G\NexusTest`, SID `S-1-5-21-3218463879-272414157-1910845735-1005`, through a documented, least-privilege OS/Host facility. The controller must be able to bind that token to the created process and independently verify the effective SID, logon/session identity where relevant, non-administrator state, and process creation result. No password value, owner credential, broad impersonation right, or token handle may cross into the restricted process or evidence.

**Decision:** no currently evidenced token source satisfies the accepted architecture without password transfer, privileged-service expansion, or another unaccepted trust-boundary change. Option A implementation and implementation experimentation remain prohibited. An amendment seeking to exit this decision's Option A HOLD must identify one concrete OS/Host token source, its provisioning and revocation, who can invoke it, exact privileges, token-handle custody, how the owner independently verifies the created process, and why this is not a general broker. Password transfer and privileged broker/service approaches do not satisfy these Option A exit criteria. If either is ever considered, it requires a separate explicit architecture alternative decision and separate owner acceptance, including explicit treatment of any conflict with A0–A6 or the E2B protocol. This decision does not authorize either approach.

## 5. Required launch contract if a token source is later accepted

These are **conditional design requirements**, not permission to implement or test.

1. **Identity and executable.** The trusted controller resolves and checks the exact reviewed executable bytes and immutable path, binds one attempt ID, and creates one process with the approved `NexusTest` primary token. It independently queries the created process token and binds SID, creation time, process ID, executable identity, and controller-held process handle. A child-supplied SID, PID, hash, or status file cannot substitute for this observation. A different SID, token type, elevation, session, executable, or parent/controller binding is a hard stop.
2. **Environment.** Construct a new Unicode environment block from a closed allowlist; do not inherit or copy the owner or interactive-shell environment. For pre-creation G0, the names are exactly `SystemRoot`, `WINDIR`, bounded `PATH`, `TEMP`, `TMP`, and `USERPROFILE`, with reviewed nonsecret values. No E2B credential, bearer/OIDC variable, proxy userinfo, unknown `*_TOKEN`/`*_KEY`, shell profile, or envd token is present. A future one-process envd-token input is a separate post-G0/G1-release matter under the accepted protocol; it must never appear in arguments, logs, or evidence. Record names and nonsecret path/configuration identity only, never secret values or hashes.
3. **Handles.** Default to **no inherited handles**. If the exact probe requires standard streams, create only the necessary streams and use an explicit OS handle allowlist for those handles; reject every other inheritable handle, including owner credential, process, file, socket, pipe, browser, and SDK handles. Record the creation flag/attribute-list policy and the approved count/type of inherited streams from the trusted launcher. A child handle count, handle flags, or 34–35 observed inheritable handles is not proof of a clean launch. Windows documents `bInheritHandles=FALSE` for no inheritance and `STARTUPINFOEX` with `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` for a specific inherited set; see [Creating Processes](https://learn.microsoft.com/en-us/windows/win32/procthread/creating-processes) and [process inheritance](https://learn.microsoft.com/en-us/windows/win32/procthread/inheritance).
4. **Directories and read boundary.** Pin the protected work directory to `C:\Users\NexusTest\AppData\Local\Nexus\E2B-G0-Host-Isolation\work` and `TEMP`/`TMP` to `C:\Users\NexusTest\AppData\Local\Nexus\E2B-G0-Host-Isolation\tmp`, or require a separately reviewed versioned path change. Resolve reparse points and ACLs at launch; require `NexusTest` ownership/binding, only the fixed synthetic work fixture, and an empty temp directory before launch. Both remain outside the owner profile, Nexus repository, and existing feasibility evidence root. The restricted process must not gain the De Yong repository, owner-only evidence, CredMan store, or other secret-bearing paths.
5. **Lifecycle and cancellation.** The controller retains the exact process and thread handles. Any proposed Job Object containment must be established before a child can execute, disallow breakaway, cover descendants, and support a bounded cancel/terminate/wait check. A stopped local process does not prove cancellation of an already dispatched E2B request or settlement of remote effects/cost. Timeout, disconnect, or cancellation leaves those outcomes unresolved until separately reconciled. [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) are a candidate native primitive, not a qualified configuration here.
6. **Owner-verifiable attestation.** The trusted creator, not the restricted child, records the attempt/configuration digest, pinned launcher/executable identities, token source and checked SID, launch API result, exact nonsecret environment-name/value policy, work/TEMP path and ACL checks, handle policy and approved stream list, process creation identity, job membership, and cancellation/exit observations. Bind all facts to one process creation and a monotonic local sequence. The owner must verify provenance and integrity of this controller record against independent OS observations where available. A child XML/status file, Security event alone, source-code assertion, or hash of an unobserved binary does not prove the full launch contract. Secret values, token fingerprints, opaque signed URLs, command-line credentials, and raw environment dumps are excluded.

### Security risks and residual `UNKNOWN`s

The unresolved risks are token acquisition and privilege escalation; a mutable executable, DLL or working path; reparse/ACL drift between check and launch; accidental inheritance or duplication of a secret-bearing handle; a forged or replayed status record; unobserved descendant/breakaway behavior; sensitive arguments or environment values entering OS logs; and a local cancellation being mistaken for remote E2B effect settlement. The current acceptable token source, independently bound process-creation record, actual minimal environment, exact inherited-handle set, descendant containment, and complete owner-secret exclusion remain `UNKNOWN`. No combination of the positive preparatory checks promotes these facts to PASS.

## 6. Acceptance gate before any implementation experiment

All of the following are required **before** building, installing, or running a launcher experiment:

1. A separate versioned token-source/trust-boundary amendment names an actual, callable source for the `NexusTest` primary token and proves that it needs neither password transfer nor a privileged broker/service. An approach requiring either cannot satisfy this decision's Option A exit-from-HOLD criteria; any future consideration requires a separate explicit architecture alternative decision and separate owner acceptance. It cannot be authorized through this Option A amendment.
2. The owner explicitly accepts the exact amendment and separately authorizes one bounded, local, synthetic launcher experiment. Acceptance of this HOLD document by itself is not that authorization.
3. An independent security review approves the launcher's fixed inputs, binary/source custody, executable-path and ACL checks, token rights, environment construction, zero/allowlisted handle inheritance, evidence provenance, cancellation design, and failure cleanup. No arbitrary command, generic runtime, credential transfer, repository access for `NexusTest`, or frozen R2/R4/R5 modification is included.
4. The experiment protocol predeclares exact success and failure observations for the same process: owner-observed token provenance and SID, fixed work/TEMP, environment names and nonsecret values, handle allowlist, absence of owner secret exposure, descendant containment, cancellation acknowledgment, and cleanup. Any observation available only from the restricted subject remains `UNKNOWN` until independently verified.
5. The experiment is local and secret-free: no E2B Sandbox, API key, envd token, guest command, provider compute, G2 dispatch, production data, or qualification promotion. It counts neither as E2B G0 completion nor as a G2 Host binding.

## 7. Rollback, abandon, and downstream gates

Abandon this decision's Option A path if the only token source requires password handling by the launcher, LocalSystem/`SeTcbPrivilege`, a privileged broker/service, owner credential access by the restricted process, unreviewed ACL expansion, or an unverifiable launch. Password transfer or a privileged broker/service cannot exit this HOLD; any future consideration requires a separate explicit architecture alternative decision and separate owner acceptance. Also abandon a proposed experiment if it cannot bind the exact binary and paths, constrain inherited handles, contain descendants, or produce owner-controlled evidence without secrets. Do not weaken the E2B protocol, claim a simulation PASS, switch to another executor, or create a Sandbox to resolve these unknowns.

If a later authorized local experiment starts, its rollback plan must terminate the exact process tree, verify no active experiment process remains, remove only its newly introduced launcher registration/configuration and temporary synthetic resources, and retain status-only failure/cleanup evidence. An ambiguous cancellation or cleanup remains `UNKNOWN`; no automatic retry or replacement launch follows.

Even an accepted, positively observed launcher would close **only the Host launch prerequisite**. E2B G0 would still require every fresh provider/account, one-Sandbox, exact configuration, observation, cleanup, and cost gate. G1 release and first untrusted execution remain separately unauthorized. G2 would still require a positively qualified complete Host binding, governed authority/budget/effect controls, useful bounded execution, interruption recovery, reconciliation, regression, independent review, and owner acceptance. Launcher acceptance is not E2B qualification, `ITEM_B PASS`, or G2 acceptance.

## 8. Decision classification and change control

This document is the **additive architecture decision** for the confirmed blocker. It preserves the accepted A0–A6 text and its frozen references; it does not re-accept or supersede them. The narrow-adapter allowance explains why a fixed-purpose launcher can be considered, but it cannot manufacture a token source or attestation. Because no current source passes Section 4, moving from Option D to an implementable Option A requires the formal amendment and explicit re-acceptance described in Section 6. That Option A amendment may be a new companion rather than an in-place edit to frozen A0–A6, provided it adds no contradiction. Password transfer or a privileged broker/service belongs only to a separate explicit architecture alternative decision with separate owner acceptance; any affected frozen architecture or E2B protocol would require explicit new versions and re-acceptance. This decision supplies no authority for that alternative.

This proposed decision is not a runtime input, an approval artifact, a conformance record, or a request to run the next experiment. No MANIFEST, portable-package allowlist, frozen document, source file, test, tag, or branch ref is changed in this preparation step. Manifest/release integration belongs to a separately authorized acceptance step if the owner accepts an exact future document state.
